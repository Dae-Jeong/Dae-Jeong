# 재구축 서사 재프레이밍 + 홈 후킹 설계 (2026-08-13)

user:
> "과연 백엔드 입장에서 시스템을 전면 갈아엎은게 과연 얼마나 메리트가 있을까?
> 오히려 관련해서 사이드 이팩트나 이런걸 더 걱정할것 같은데 말이야"
> "어떻게 풀어야 아 이사람은 리팩토링이나 기술부채를 잘 해결하는구나 하는 인상을 줄 수 있을까?"
> "어떤걸 중점적으로 어필해야 딱 이목을 끌고 그 내용이 궁금해서 들어가게 되는지 설계를 잘 못한것 같아"

## 1. 문제 진단 — "전면 재구축"은 기본값이 마이너스다

경력 있는 백엔드 리더에게 rewrite는 **가장 유명한 실패 패턴**이다. 방어 없이 쓰면 읽는 사람은 이렇게 받는다:

| 우리가 의도한 것 | 실제로 읽히는 것 |
| --- | --- |
| 문제를 근본에서 해결했다 | 돌아가는 걸 못 참는 사람이다 |
| 36시간에 해냈다 | 검증을 건너뛴 것 아닌가 |
| 전면 재구축 | blast radius를 통제 못 하는 사람이다 |
| 반대를 설득했다 | 조직을 밀어붙인 사람이다 |

**핵심 문제**: 우리 사실들은 이미 이 의심을 전부 반박하는데, 문안이 그것들을 *성과*로만 쓰고
*리스크 통제 증거*로 쓰지 않는다.

## 2. 이미 가진 방어 재료 — 전부 사실이고 registry에 있다

| 의심 | 반박 사실 | claim |
| --- | --- | --- |
| blast radius를 통제 못 한다 | **FE(Next.js)는 유지하고 backend만 분리 교체** — 전면이 아니라 경계를 그었다 | `thready.rebuild-decision-execution` |
| 아무 때나 갈아엎는다 | **서비스가 작은 시점**이라는 조건부 판단 — 비용이 가장 싼 타이밍을 골랐다 | 〃 |
| 대안 검토 없이 질렀다 | 부분 수정을 검토했고 **왜 안 되는지**(의존성 구조 잔존) 근거를 댔다 | 〃 |
| 검증 없이 빨리 했다 | **하네스를 먼저 세우고** 그 규칙 위에서 작업 — 36시간은 그 결과이지 생략의 결과가 아니다 | 〃 |
| 사이드이펙트가 터졌을 것 | **재발률이 오히려 37% → 11%로 감소** | `thready.qa-reopen-reduction` |
| 던지고 떠났다 | cutover 이후 **개발·운영 전담**, 월 수만 건 5xx 0.3% | `thready.production-operation-quality` |

### 가장 중요한 재프레이밍

**`reopen 37% → 11%`는 "개선 지표"가 아니라 "사이드이펙트를 통제했다는 증거"다.**

재작성의 전형적 실패 모드는 *새 버그 폭증*이다. 그런데 우리는 재구축 이후 **재발이 3분의 1로
줄었다.** 이건 성능 자랑이 아니라 **리스크가 현실화되지 않았음을 지표로 증명한 것**이다.
지금 문안은 이걸 그냥 성과 숫자로 쓰고 있어서, 읽는 사람 머릿속의 의심과 연결되지 않는다.

## 3. 반대 증거도 이미 있다 — "갈아엎기만 하는 사람"이 아니다

흩어져 있어서 안 읽히는 **점진적 개선 이력**:

- `centurion.async-migration` — Celery → TaskIQ **점진 전환**, 알림 도메인 분리
- 스튜디오랩 — Node.js 레거시의 **NestJS 이관** (버리지 않고 옮김)
- `nexus.backend-architecture` — monorepo **service boundary와 migration flow** 주도
- `be-template.*` — 기존 구조를 표준으로 **일반화**

→ 재구축은 **여러 선택지 중 하나였고 조건이 맞아서 골랐다**는 것을 보여주는 재료다.
한 줄이라도 병기하면 "rewrite 애호가"가 아니라 **"부채를 언제 갚을지 계산하는 사람"**이 된다.

## 4. 확정 프레이밍 — 부채 상환 시점 계산자

```
"갈아엎었다"  →  "지금 갚는 비용과 나중에 갚는 비용을 비교했고,
                 서비스가 작을 때가 가장 싸다고 판단했고,
                 범위를 backend로 한정해 blast radius를 줄였고,
                 하네스를 먼저 세워 검증 가능하게 만들었고,
                 재발률로 리스크가 현실화되지 않았음을 증명했다"
```

문장 규칙:
- **"전면"을 단독으로 쓰지 않는다.** 항상 범위 한정(FE 유지 / backend만)과 함께 쓴다.
- **36시간 옆에 하네스를 붙인다.** 숫자만 두면 "졸속"으로 읽힌다.
- **reopen 지표를 재구축 리스크와 같은 문장에 둔다.** 떨어뜨리면 방어가 안 된다.
- 점진 개선 이력을 **같은 축 안에** 둬서 선택지가 있었음을 보인다.

## 5. 홈 후킹 설계 — 성과 나열에서 질문 유발로

### 진단

현재 홈 Summary 4행은 전부 "무엇을 했다"의 나열이다. 정보는 정확한데 **클릭할 이유가 없다.**
스크롤을 멈추게 하는 것은 성과의 크기가 아니라 **"어? 그건 어떻게 한 거지?"** 하는 결손감이다.

### 후킹 강도 순위 (반직관성 기준)

| 재료 | 후킹 | 이유 |
| --- | --- | --- |
| 품질 기준값이 **자사 출력을 되먹이고 있었다** | ★★★ | 측정을 믿었는데 측정이 틀렸다 — 직접 겪지 않으면 못 쓰는 문장 |
| 판정을 writer에 뒀더니 **18건 전부 미발동** | ★★★ | 구체적 실패 + 왜 그런지 궁금해짐 |
| 재구축했는데 **재발이 오히려 줄었다** | ★★☆ | 반직관 (보통 재구축 = 버그 폭증) |
| 파악부터 재구축까지 **36시간** | ★★☆ | 숫자가 이상하게 작아 이유를 묻게 됨 |
| 3층 판정 체계 | ★☆☆ | 설명적 — 이해는 되지만 궁금하지 않다 |
| 연구소장·Tech Lead·PO 병행 | ★☆☆ | 신뢰 신호이지 후킹은 아님 |

### 원칙

- **각 줄은 답이 아니라 질문을 남긴다.** 답은 Portfolio에 있고, 그게 클릭 이유다.
- **실패·발견을 앞에 둔다.** 성공 나열은 누구나 쓰지만 "내가 틀렸던 지점"은 겪은 사람만 쓴다.
- 신뢰 신호(직함·병행)는 **뒤로**. 후킹이 먼저 걸리고 나서 검증받는 순서다.
- 단, TheLadders 원문상 **직함·회사·기간은 별도로 항상 상단 노출** — 후킹과 다른 층이다
  (홈 Hero chip, 이력서 헤더가 그 역할).
