## 0. v3 규칙 요약 (감사 체크리스트)

| # | 규칙 | 판정 방법 |
| --- | --- | --- |
| R1 | 명사형 종결 | bullet이 `~했다/~한다/~했습니다`로 끝나지 않는다 |
| R2 | 수치·주제어 문두 | 각 줄의 첫 2~3어절에 정보가 있다 (수치가 끝에 묻히지 않는다) |
| R3 | 블록당 3~5줄 | 6줄 이상 금지 |
| R4 | 줄당 1~2행 | 3행 이상은 문단이다 |
| R5 | 판단 줄 유지 | 각 프로젝트에 판단·근거 줄이 최소 1개 |
| R6 | hot zone | 최신 경력 첫 블록 첫 줄에 최강 수치 |
| R7 | 정성 표현 금지 | "훨씬", "긍정적", "많은" 등 |
| R8 | 소개(L1)는 문단형 | 개조식으로 쪼개지 않는다 |

## 1. 감사 결과 — 웹 이력서 `app/fe/app/resume/resume-view.tsx`

### 1-1. Summary (KO) — R2·R4 위반

현재 5줄 중 3줄이 3행 이상이고, 수치가 문장 끝에 묻혀 있다.

| 현재 | 문제 | 판정 |
| --- | --- | --- |
| `AI 제품만 4년째 만들고 있다 — 모델을 만들다 기획을 거쳐…` | R1(`있다`) · 길이 | 개선 |
| `백엔드를 택한 데는 이유가 있다 — AI가 구현을…` | R1 · R4(3행) · 도입부가 정보 없음 | 개선 |
| `기업부설연구소장·Tech Lead·PO 역할을 병행하며…` | 양호 (주제어 문두) | 유지 |
| `문제의 경계를 다시 잡고, 측정과 게이트로…` | R4(3행) · 일하는 방식 섹션과 중복 | 축약 |
| `CES 2024 Best of Innovation 수상 제품의 PM 메인 역할 — …` | 양호 | 유지 |

**단, Summary는 L1(소개)에 가까운 영역이다.** §10은 소개의 문단형 유지를 규정한다.
→ 판단: Summary는 **완전 개조식으로 바꾸지 않는다.** R2(수치 문두)·R4(길이)만 적용하고
서술 어미는 유지한다. 이 문서의 [쟁점 A](#쟁점) 참조.

### 1-2. 대표 프로젝트 — Thready — R3 위반 (6줄)

6줄 → 5줄로 줄여야 한다. 후보:
- `AI 모듈 확장을 근거로 FastAPI 분리 도입` 줄과 `cutover 이후 QA 재발률` 줄의 운영 수치 통합
- 또는 `품질 기준값 자기 되먹임` 줄을 포트폴리오 상세로 이관 (홈/이력서에서는 1줄 절약)

**hot zone(R6)**: 현재 첫 줄이 `AI 도구로 빠르게 구축돼 재발 이슈 통제가 어려웠던…`으로
시작해 **36시간 수치가 3행 끝에 있다.** 가장 비싼 한 줄이 정보 없이 시작한다.
→ `QA 버그 재발률 37% → 11%` 줄을 첫 줄로 올린다.

### 1-3. 경력 섹션 — 구조 불일치

MediSolve만 bullet 3줄, 나머지 4곳은 **한 줄 서술형**이다.

| 경력 | 현재 | 문제 |
| --- | --- | --- |
| MediSolve AI | bullet 3줄 | 양호 |
| 더데이랩스 | 1줄 서술 | 판단 줄 없음(R5) |
| Memento AI | 1줄 서술 | 판단 줄 없음(R5) |
| STUDIO LAB | 1줄 서술 (특허 인과 포함) | 길이 3행 |
| 아이즈솔 | `Vision AI에서 시작한 AI product engineering 경력 (인턴)` | **내용 0** — 무엇을 했는지 없음 |

→ 아이즈솔이 가장 큰 구멍이다. 경력 한 줄이 아무 정보도 주지 않는다.

### 1-4. EN — 별도 판단 필요

영어권은 front-loading·XYZ가 맞다. **EN에는 v3(한국어 개조식)를 적용하지 않는다.**
EN은 동사 원형 시작(`Rebuilt`, `Reduced`, `Designed`)으로 정렬하는 것이 맞다.
현재 EN도 KO 구조를 그대로 번역한 형태라 별도 정렬 대상. → 이번 범위에서 제외, 후속.

## 2. 감사 결과 — 홈 `app/fe/app/page.tsx`

Summary 4행은 2026-08-12에 v6 정체성으로 교체했다. v3 기준 재검토:

| 현재 | 판정 |
| --- | --- |
| `AI가 만든 결과물의 품질을 자동 게이트·실측 분포 대조·사람 판정 세 층으로 나눠 판정 가능하게 만듦` | R1 ✅(만듦) · R2 △ (수치 없음, 주제어는 앞) |
| `AI 콘텐츠 생성 backend 전면 재구축 — QA 티켓 reopen 비율 37% → 11%, …` | ✅ |
| `생성 파이프라인을 planner·writer 역할로 분리 설계·구현 — …` | ✅ |
| `Backend Engineer로 합류해 기업부설연구소장·Tech Lead·PO 역할 병행 — …` | ✅ |

**R6 위반**: hot zone 규칙상 **가장 강한 수치(37% → 11%)가 2번이 아니라 1번**에 와야 한다.
현재 1번은 수치가 없다.

→ **개선안: 01과 02의 순서를 바꾼다.** 홈은 "15초 검증 관문"이므로 hot zone 효과가 가장 크다.

## 3. 감사 결과 — 포트폴리오 `case-details.tsx`

Thready case를 오늘 개정했으나 `problem`·`decisions`·`system`이 **전부 서술형 문단**이다.
포트폴리오는 이력서보다 정독 비중이 높은 지면이므로 **전면 개조식 전환은 부적절**하다.
단 `system` 4~5개 항목의 `desc`는 스캔 대상이므로 명사형 종결로 정리 가능.

→ 우선순위 낮음. 홈·이력서 이후.

agent 답변은 **대화체**다. 개조식 대상 아님. 변경 없음.

## 쟁점 — Codex 리뷰 대상

- **A. Summary/소개의 경계**: 웹 이력서 Summary는 L1(소개)인가 L2(경력 설명)인가?
  L1이면 문단형 유지, L2면 개조식. 현재는 중간 형태다.
- **B. 웹 이력서 vs 플랫폼 프로필**: 웹은 스크롤 지면이고 플랫폼은 폼 필드다.
  같은 v3를 적용하는 게 맞나, 웹은 더 길어도 되나?
- **C. hot zone 우선순위 vs 서사 순서**: 재구축 서사는 "문제 → 판단 → 실행 → 성과" 순이
  자연스러운데, hot zone은 성과를 맨 앞에 요구한다. 어느 쪽이 우선인가?
- **D. 아이즈솔 보강 시 강도**: 인턴 경력의 정량(99.8% 등)은 recency weighting으로
  공개 미사용 확정. 수치 없이 어떻게 내용을 채우나?

## Codex 리뷰 결과 (2026-08-12, gpt-5.6-sol · xhigh · read-only)

### 쟁점 판정 — 4건 전부 수용

| 쟁점 | 판정 | 근거 |
| --- | --- | --- |
| **A. 웹 이력서 Summary** | **L1 (소개)** | 헤더 한 줄이 L0, Summary는 정체성·현재 역할·차별점 설명 → 문단형 유지. 개조식 전환하지 않는다. 단 현재 `PlainList` 5줄은 L1치고 과다 |
| **B. 웹 vs 플랫폼** | **포맷 규칙 분리** | 사실·claim 강도·최신 우선만 공유. 웹 이력서는 포트폴리오로 넘기는 관문이라 더 압축, 플랫폼 경력 상세에만 v3 3~5줄 적용 |
| **C. hot zone vs 서사** | **성과 우선** | `성과 → 문제·판단 → 실행`. 판단을 버리는 게 아니라 정독 단계로 배치 |
| **D. 아이즈솔** | **수치 없이 contributed 1줄** | recency 규칙상 초기 경력 1 bullet 이하, `led/owned` 금지. **판단 줄을 억지로 넣지 않는다** — 대안 검토 evidence가 없으므로 §6 위반 |

**D의 교정이 중요하다**: R5("각 프로젝트에 판단 줄 최소 1개")는 기계적이어서
"evidence 있는 결정에만 판단을 쓴다"는 §7 체크리스트와 충돌한다. → **R5를 완화한다.**

### 검증한 지적 — 전부 사실로 확인됨

1. **`planner·writer`가 claim registry에 없었다** — 홈·KO/EN 이력서·포트폴리오에 공개 중인데
   stable claim ID 부재. → `thready.agent-pipeline-design` 신설 (owned, forbidden: 오케스트레이션
   프레임워크 경험으로 표현 금지, 18건을 평가셋 규모로 확대 해석 금지).
2. **`기업부설연구소장`이 registry에 없었다** — canonical-baseline에는 user-confirmed로 있으나
   claim 계약 밖. → `career.medisolve-role-evolution` allowed_copy에 추가 + note로
   "연구소장은 등재 직함, Tech Lead·PO는 역할 병행" 구분 명시.
3. **`AI 제품만 4년째`가 계약 위반** — `career.tenure` allowed_copy는 `4년차`/`실무 4년차`다.
   게다가 **"AI 제품만"은 사실과 다르다** (메멘토 예약·결제 backend는 AI 제품이 아니다).
   → `AI 제품을 만들어온 실무 4년차`로 교체.
4. **37% → 11%의 인과 단정** — `thready.qa-reopen-reduction` forbidden에
   "backend 단독 효과로 단정 (BE/FE 분리 불가)"가 있다. 홈·이력서의 `재구축 — 37% → 11%`는
   직접 인과로 읽힌다. → **`cutover 전후 관측에서`** 를 KO/EN 전부에 명시.
5. **`data-claim` 속성 0건** — "모든 성과 문장은 검증된 claim registry의 public 표현만
   사용합니다"라는 안내가 코드에 있으나 추적 장치가 없다. → 후속 과제로 등록.

### 조사 근거 보정 — 원문 대조로 확인

Codex가 "80%는 상단 1/3이 아니다"라고 지적해 **TheLadders 원 보고서 PDF를 직접 열어 확인했다.**

- 원문: **6초** (7.4초 아님) · "recruiters spend only 6 seconds reviewing an individual resume"
- 원문: 리뷰 시간의 **80%는 6개 데이터 포인트**(이름·현 직함/회사·전 직함/회사·현직 기간·전직
  기간·학력)에 쓰인다. **"상단 1/3 hot zone 80%"는 우리가 만든 오류다.**
- 원문: 그 밖의 본문은 **"filler ... little to no impact on the initial decision making"**
- "첫 2~3단어만 읽힘 보장"·"F자 패턴"은 원문에 없다 — 2차 출처(블로그)다. hard rule에서 제거.

**결론이 바뀐 지점**: 6초 판정을 좌우하는 것은 bullet이 아니라 **직함·회사·기간**이다.
→ 웹 이력서 헤더에 현직/전직·기간이 없었다 (이름·직군·한 줄만). **최우선 결함이었다.**
