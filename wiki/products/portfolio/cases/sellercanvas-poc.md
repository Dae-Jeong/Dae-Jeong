## Executive Summary

PM을 주 역할로 생성형 AI 커머스 제품의 고객 흐름·기능 범위·출시 우선순위를 정해 prototype을 v1.0 제품으로 구체화했습니다. 이후 외부 패션 브랜드의 비즈니스 요구를 기술 검증 범위로 바꿔 PoC를 진행했습니다.

## My Scope

- prototype에서 v1.0까지 제품 흐름·기능 범위·출시 우선순위 구체화
- 외부 기업 PoC의 기획·일정 관리·기술 검증과 요구사항의 technical scope 전환
- 상세 페이지 제작 흐름 재설계 과정 참여
- 제품 전체 단독 기획·총괄 또는 backend engineering 사례로 확대하지 않음

## Problem And Constraints

기술 prototype이 실제 사용 가능한 제품이 되려면 어떤 고객 흐름을 남기고 어떤 기능을 먼저 출시할지 정해야 했습니다. 외부 기업 PoC에서는 기존 제품을 그대로 시연하는 것이 아니라, 상대 조직의 업무 요구를 제한된 기간 안에 검증 가능한 제품 범위와 기술 항목으로 바꿔야 했습니다.

이 시기의 주 역할은 PM입니다. Vision AI와 backend 경험을 활용해 기술 제약을 함께 판단했지만, 현재 backend 전문성의 직접 근거로 포장하지 않습니다.

## Decision And Alternatives

- prototype의 기능을 모두 확장하기보다 고객이 실제로 따라갈 핵심 흐름과 출시 우선순위를 먼저 정했습니다.
- 외부 기업의 비즈니스 요구를 기능 목록으로 바로 옮기지 않고, 제품 흐름·데이터 입력·AI 처리·결과물 확인의 기술 검증 항목으로 나눴습니다.
- PoC 과정의 피드백을 상세 페이지 제작 흐름 재설계에 연결했습니다.

## System Design And Implementation

diagram: 기업 요구 -> 고객 workflow·성공 조건 -> 제품 범위 -> AI 기술 검증 -> prototype/v1.0 -> PoC feedback

- 제품 흐름과 기능 범위, 일정, 출시 우선순위를 하나의 delivery plan으로 관리했습니다.
- 기술팀과 비즈니스 요구를 공유할 때 검증할 입력·처리·출력 범위를 구분했습니다.
- 상세 페이지 제작 흐름에서 나온 결과는 「페이지 출력 방법」 특허로 출원·등록됐습니다.

## Failure Modes And Operation

- PoC의 요구를 일반 제품 범위로 그대로 흡수하지 않고, 제한된 검증 범위와 v1.0 공통 흐름을 구분했습니다.
- 외부 기업의 요구와 AI 기술 가능성이 어긋날 때 일정·범위·검증 항목을 다시 조정했습니다.
- PoC 이후의 고객사 운영 성과나 매출 효과는 확인된 근거가 없어 주장하지 않습니다.

## Evidence, Result, And Limits

- User-confirmed: SellerCanvas를 prototype에서 v1.0 제품으로 구체화하는 구간을 PM 메인 역할로 이끌었음. `led`.
- User-confirmed: 외부 패션 브랜드 PoC에서 기획·일정 관리·기술 검증과 business requirement의 technical spec 전환을 담당함. `led/medium`.
- Source-backed: 제품은 CES 2024 Best of Innovation을 수상함. 개인 단독 성과가 아닌 product outcome.
- User-confirmed/source-backed: 상세 페이지 제작 흐름에서 특허 「페이지 출력 방법」이 출원·등록됨. 단독 발명은 주장하지 않음.
- Limits: 고객사 실명·개수, 제품 전체 단독 기획, PoC의 production adoption·매출 성과, backend 구축 ownership은 주장하지 않음.
