# 섹션 제목 대 본문 위계 검토 (2026-08-13)

user: "title, description, 내용이 좀 명확하게 비교가 잘 안되는것 같아 / 제목에 비해 설명 글자크기가 큰가?"
지시: "위계 관련된 내용은 daejeong design 활용해서 개선 검토"

## 1. 먼저 확인한 것 — 구현은 계약을 지키고 있다

`app/design`은 **확정본 스냅샷이고 직접 수정 금지**다 (D2에서 작업 후 승격).
따라서 "구현이 계약에서 벗어났는가"부터 갈랐다.

| 대상 | 확정 프로토타입 (`root-v3-prototype.html`) | 구현 (`app/fe`) | 판정 |
| --- | --- | --- | --- |
| 섹션 제목 | `.section-head h2` — `--text-xl` **22px**, display, 600, `-0.01em` | `text-xl font-semibold tracking-[-0.01em]` | ✅ 일치 |
| Summary 본문 | `.summary__text` — `--text-lg` **18px**, weight 450 | `text-lg font-[450]` | ✅ 일치 |
| 토큰 값 | xs12 · sm13 · base16 · lg18 · xl22 · 2xl28 · 3xl40 · 4xl56 · cred14 | `globals.css @theme` 동일 | ✅ 일치 |
| 폰트 | `--font-display` = `--font-mono` = IBM Plex Mono (동일 폰트) | `font-mono` | ✅ 일치 |

**구현 이탈이 아니다.** 위계가 약한 것은 **계약 자체의 값**에서 온다.

## 2. 왜 평평하게 읽히는가

### 2-1. 인접 단계 비율이 1.22다

```
섹션 제목 22px  /  본문 18px  =  1.22
```

모듈러 스케일에서 1.22는 **인지 가능한 최소치 부근**이다. 제목과 본문이 붙어 있고 색·굵기 차이만
있으면 "크기가 다르다"보다 "굵기가 다르다"로 읽힌다. 사용자가 "설명 글자가 큰가?"라고 느낀 지점이다.

### 2-2. 한글에서는 격차가 더 줄어든다

`font-mono`(IBM Plex Mono)에는 **한글 글리프가 없다.** 섹션 제목이 `요약`·`할 수 있는 일`처럼
한글이면 `--font-ko`(Pretendard)로 폴백한다. 즉 제목과 본문이 **같은 폰트 22px vs 18px**가 되어,
라틴 문자에서 기대한 mono 특유의 형태 대비가 사라진다.

→ 영문 프로토타입에서 검증된 위계가 한글 화면에서는 **1.22 크기 차이 하나로만** 남는다.

### 2-3. 스케일 상단이 비어 있다

| 단계 | px | 실사용 |
| --- | --- | --- |
| xs | 12 | 121 |
| sm | 13 | 66 |
| base | 16 | 22 |
| lg | 18 | 18 |
| **xl** | **22** | **10** ← 섹션 제목 |
| **2xl** | **28** | **5** |
| 3xl | 40 | 11 |
| 4xl | 56 | 6 |

`2xl(28)`은 스케일에 정의돼 있으나 거의 안 쓰인다. **제목용 한 단계가 비어 있는 상태**로
제목이 본문 바로 위 칸(22)에 앉아 있다.

## 3. 개선안 — 3가지 비교

| 안 | 내용 | 제목:본문 | 장점 | 위험 |
| --- | --- | --- | --- | --- |
| **A. 섹션 제목 22 → 28** | `SectionHead h2`만 `text-2xl` | **1.56** | 기존 토큰 사용, 본문 가독성 손대지 않음, 빈 단계 활용 | 섹션 헤더가 커져 스캔 밀도 하락 가능 |
| B. 본문 18 → 16 | `summary__text`를 base로 | 1.375 | 정보 밀도 상승 | **base 16 앵커 결정의 근거**(40+ 채용 담당자 독자·업계 실측)와 충돌. 홈 Summary는 1차 판정 문장이라 축소가 손해 |
| C. 제목에 형태 대비 추가 | uppercase·letter-spacing·색 | 1.22 유지 | 크기 변경 없음 | 한글은 uppercase가 없어 **한글 화면에서 무효** |

**추천: A.** 근거 —
- 토큰을 새로 만들지 않는다 (계약의 빈 단계를 채운다).
- 본문 16px 앵커 결정을 건드리지 않는다 (그 결정에는 독자 연령·업계 실측 근거가 붙어 있다).
- 한글에서도 유효하다 (C와 달리 폰트·대소문자에 의존하지 않는다).
- 섹션 헤더는 `border-bottom`과 `no`·`meta`를 이미 갖고 있어 28px에서도 과하지 않다.

부수 조정 (A 채택 시):
- `SectionHead`의 `no`·`meta`는 `xs(12)` 유지 — 제목이 커질수록 라벨 대비가 오히려 선명해진다.
- `Selected Proof`의 케이스명이 현재 `text-xl(22)`로 **섹션 제목과 동일 크기**다.
  제목이 28로 오르면 자연히 한 단계 아래가 되어 위계가 정리된다 (추가 수정 불필요).
- `Explore` 라우트 카드의 이름과 설명이 **둘 다 `text-sm(13)`**으로 같은 크기다.
  이름을 `base(16)`으로 올리면 카드 내부 위계도 함께 해소된다. → **A와 별개 항목으로 제안**.

## 4. 절차 — 이건 D2 개정 사안이다

`app/design/README.md`: *"이 폴더에서 직접 수정하지 않는다 — D2에서 작업하고 확정 시 재승격."*

구현이 계약을 지키고 있으므로, `app/fe`만 고치면 **구현이 확정본에서 이탈**한다.
정상 경로는 다음과 같다:

1. D2 "Profile" 프로젝트에서 `root-v3-prototype` 타입 스케일 개정 (섹션 제목 22 → 28)
2. 확정 후 `app/design/`으로 재승격
3. `app/fe` 구현을 승격본에 맞춰 반영
4. 스펙의 **Type scale 계약** 문구 개정 (2026-07-18 9차 라운드 → 개정 이력 추가)

**사용자 결정 필요**: 위 정식 절차를 밟을지, 아니면 `app/fe`에 먼저 적용해 실제 화면에서 확인한 뒤
확정되면 D2로 역승격할지. 후자는 빠르지만 그동안 구현이 확정본과 어긋난 상태로 남는다.

## 5. 검토하며 함께 발견한 것

- `Explore` 카드: 이름 `text-sm(13)` = 설명 `text-sm(13)` — **카드 내부 위계 없음.** 굵기·대문자만 다르다.
- 홈 hero 한 줄(`text-xl` 22)과 섹션 제목(22)이 같은 크기 — 역할이 다른데 같은 층으로 읽힌다.
  A안 적용 시 자연 해소된다.

| 문안, claim, 성과 서술, 회사별 역할 기술 | **wiki canonical** | evidence·claim registry → canonical → 파생(플랫폼·`app/fe`) |

**회색지대 — 정보 배치(섹션 순서)**: 디자인 취향이 아니라 근거로 결정한다.
경력 섹션을 05 → 02로 올린 것은 TheLadders 원문(리뷰 시간의 80%가 이름·현/전 직함·회사·기간·학력)에
근거하므로 문안 쪽 결정으로 처리했다. 근거 없이 배치만 바꾸는 경우에는 D2를 거친다.

→ **이번 D2 승격 범위는 타이포그래피로 한정된다**: 섹션 제목 `xl(22)` → `2xl(28)`,
Explore 카드 이름 `sm(13)` → `base(16)`, `/resume` 헤더 4줄 재배치 + 9차 base-16 정렬.
경력 섹션 문안·순서 변경은 승격 대상이 아니다.
