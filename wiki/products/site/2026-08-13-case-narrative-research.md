# 케이스 서술 구조 검토 (2026-08-13)

user: "포트폴리오에 내용을 적을 때 문제 제기나 방안 제시 방향설정 수행 결과 이런 흐름이 필요할것 같은데,
우리가 그런게 있나 지금?" → "이런 내용을 제시하고 설명하는 그 과정에 대해서도 한번 서치를 제안해봐"

## 1. 현재 구조와 갭

```
현재    문제 → 결정 → 시스템 → 운영 근거          (4단)
PAAR    Problem → Analyze → Action → Result
매핑    ✅       ❌         ✅        ✅
```

**`Analyze`(대안 검토) 자리가 없다.** 지금은 `문제` 섹션 안에 섞여 있어
("부분 수정으로는 의존성 구조가 남는다고 봤다") 비교로 읽히지 않는다.

## 2. 국내 레퍼런스 — Analyze가 최상위 평가 축이다

[서치라이트 — 개발자 경력기술서 예시(2026)](https://blog.searchright.net/developer-career-description-examples/) 원문:

> "면접관은 Action(행동)보다 **Analyze(대안 검토)**를 중요하게 봅니다.
> **AI가 코드를 만들어도 어떤 방식을 선택하고 적용할지 판단하는 건 결국 개발자의 몫이기 때문**"

⚠️ **이 근거가 우리 정체성 문장과 같은 논리다.** v6 소개의
"AI가 구현을 점점 더 많이 맡을수록, 사람이 끝까지 책임져야 하는 층을 어떻게 지킬 것인가"와
시장이 Analyze를 중시하는 이유가 정확히 겹친다.
→ 대안 검토를 드러내는 것은 포맷 개선이 아니라 **포지셔닝의 실증**이다.

### Analyze 실제 예시 — 한 줄에 세 요소

> "DB 쿼리 병목·캐시 미적용 구간 분석, **Memcached 대비** 데이터 구조 유연성 고려해 Redis 선택"
> "Lighthouse·번들 분석으로 병목 구간 파악, **SSR 전환보다** 번들 최적화 우선 적용"

패턴: **분석 방법 + 기각한 대안 + 선택 이유**. 길지 않다. 한 줄이면 된다.

### 면접 꼬리질문이 요구하는 것

[잡코리아 — 경력직 포트폴리오 작성법](https://www.jobkorea.co.kr/goodjob/tip/view?News_No=18449) ·
[링커리어](https://community.linkareer.com/employment_data/4872430):

> "이 프로젝트를 왜 골랐어요?" · "이 기술을 왜 썼어요?" · "가장 어려웠던 부분은요?" ·
> **"다시 한다면 뭘 바꿀 건가요?"**

→ 앞의 셋은 Analyze가 답한다. **마지막 하나는 우리 구조에 자리가 없다** — 회고·한계.
부분적으로만 있다(품질 기준값 자기 되먹임 발견, opsIntro의 "주장하지 않는다").

## 3. 해외 레퍼런스 — 같은 방향, 표현이 다르다

- 채용 담당자는 **"the messy middle"** — 스케치, **검토했다가 기각한 대안**, 그 뒤의 사고 과정을 보고 싶어 한다.
- 기술적으로 훌륭한 프로젝트도 **결정의 맥락이 없으면 무너진다.** 맥락이 붙어야
  "코드 샘플"이 "이 사람이 어떻게 일하는지 보는 창"이 된다.
- 각 프로젝트는 **왜 다른 대안이 아니라 이 접근을 골랐는지**를 분명히 밝혀야 한다.

→ §6의 판정("영어권은 impact, 국내는 대안 검토")은 **경력기술서 기준에서는 맞지만
포트폴리오 기준에서는 양쪽이 같은 것을 요구한다.** 케이스 지면에서는 지역 차이가 없다.

## 4. 결론 — 5단으로 간다

```
문제 → 검토 → 결정 → 시스템 → 결과
P      A      (A의 결론)  A(ction)  R
```

`검토`를 독립 섹션으로 세운다. 이유:

1. **국내·해외 레퍼런스가 모두 최상위로 꼽는 축**인데 지금 자리가 없다.
2. `문제` 안에 섞으면 **비교가 안 보인다** — 기각한 대안이 문제 서술의 일부로 읽힌다.
3. 우리 정체성("판단은 사람 몫")의 **직접 실증**이라 다른 지면이 대신할 수 없다.

### 채우기 규칙

- **근거 있는 케이스만 채운다.** 없으면 섹션을 생략한다 — 빈 섹션은 오히려 약해 보인다(§6·§7).
- 한 줄 패턴: `분석 방법 + 기각한 대안 + 선택 이유`. 길게 쓰지 않는다.
- 케이스별 채움 가능 여부:

| 케이스 | 대안 검토 근거 | 판정 |
| --- | --- | --- |
| AI 콘텐츠 생성 backend 재구축 | 부분 수정 vs 전면 재구축, FE 유지 vs 전체 교체 | ✅ 강함 |
| 주문·재고 비동기 처리 | API 안에서 처리 vs 경계 밖 worker 분리 (메멘토 학습 전이) | ✅ 강함 |
| 조직 표준 백엔드 템플릿 | 확인 필요 | ⚠️ |
| 실시간 상담 AI 세션 | 확인 필요 (co-led이므로 강도 주의) | ⚠️ |
| 제품 운영 게이트 | **evidence에 판단 기록 없음** | ❌ 생략 |

### 함께 검토할 것 — 회고 자리

"다시 한다면 뭘 바꿀 건가요?"에 답할 자리가 없다. `결과` 섹션 끝에
**한계·다음 수** 한두 줄을 붙이는 방식이 가볍다. 별도 섹션까지는 과하다.
