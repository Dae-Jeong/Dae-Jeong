# 지면별 역할 정의 (2026-08-13)

user: "각 영역별로 역할을 좀 정의를 해볼까? 이력서 롤, 포폴 롤, 그리고 다른 롤들도"

**왜 필요한가.** 역할이 문서로 없으면 지면이 서로를 침범한다. 실제로 오늘 이런 표류가 있었다 —
이력서가 프로젝트 소개서가 됐고, Summary가 다른 섹션의 중복 요약이 됐고,
포트폴리오 목록이 프로젝트 나열로 남아 있었다.

## 0. 한 장 요약

| 지면 | 한 문장 역할 | 읽는 시간 |
| --- | --- | --- |
| `/` 홈 | **거르는 곳** — 더 볼지 말지 15초 안에 정한다 | 15초 |
| `/resume` | **판단하는 곳** — 경력과 기술 사례만으로 인터뷰 여부를 판단한다 | 첫 장 30초, 필요 시 5분+ |
| `/portfolio` | **검증하는 곳** — 세 대표 case와 supporting payment case를 한 문서에서 확인 | 30초~5분+ |
| `/portfolio/{case}` | **직접 연결하는 곳** — 호환용 case anchor·상세 route | 가변 |
| `/chat` | **묻는 곳** — 근거 범위 안에서 답한다 (Phase 2) | 가변 |
| `/blog` | **생각을 공개하는 곳** (Phase 2) | 가변 |
| `/labs` | **만든 걸 만져보는 곳** (Phase 2) | 가변 |
| 플랫폼 프로필 | **찾게 하는 곳** — 검색 유입, 홈으로 보낸다 | 가변 |

## 1. `/` 홈 — 거르는 곳

- **목적**: 15초 안에 "더 볼지" 결정하게 한다.
- **담는 것**: 이름·현직·직군(즉시 스캔) · 반직관적인 발견 3~4줄 · 다음 지면으로 가는 입구.
- **담지 않는 것**: 완결된 설명. 홈에서 답을 다 주면 클릭할 이유가 없다.
- **성공 기준**: 각 줄이 **"어? 그건 어떻게 했지?"**를 남기는가 (§12).
- **주의**: 성과 나열은 정확해도 후킹이 아니다. 실패·발견이 앞에, 직함·수상은 뒤에.

## 2. `/resume` — 판단하는 곳

- **목적**: 채용 담당자가 **적합 여부를 판정**할 수 있게 한다.
- **담는 것**: 첫 장 소개·경력·최강 근거 → **완결된 기술 사례**(문제·제약·선택·구현·검증·운영·결과) → 기술 → credentials.
- **담지 않는 것**:
  - 제품 기능을 소개하기 위한 프로젝트 설명. 기술 역량 판정에 필요한 시스템 맥락과 사례 깊이는 resume에 둔다.
  - **사내 코드명** — 읽는 사람은 모른다. 제품 성격으로 쓴다.
  - 다른 섹션의 중복 요약 — Summary가 아래 섹션을 되풀이하면 지운다.
- **성공 기준**: 회사·직함·기간이 **즉시** 보이는가. 리뷰 시간의 80%가 여기에 쓰인다(TheLadders 원문).
- **순서 원칙**: **사실(경력)이 먼저, 주장(역량 축)이 뒤.** 검증할 근거 없이 주장부터 읽게 하지 않는다.
- **역할 원칙**: 역할은 직함 나열이 아니라 `문제 소유·판단 범위·backend mechanism·운영 결과`의 반복으로 전달한다. 상세 기준은 [resume role positioning standard](../resume/role-positioning-standard.md)가 소유한다.

## 3. `/portfolio` — 한 문서에서 고르고 검증하는 곳

- **목적**: 첫 화면과 index에서 확인할 경험을 고르게 한 뒤, route 이동 없이 문제·판단·시스템·운영 근거까지 검증하게 한다.
- **headline**: `아이디어를 새로운 가치로 실현하는 메이커, 김대정입니다.`
- **primary**: Thready → Company AX → Centurion.
- **supporting**: Memento Payment.
- **담는 것**: 각 case의 맥락·책임 범위·핵심 기술 판단·고유한 시각화·검증 가능한 proof.
- **담지 않는 것**: 동일 dossier 형식의 반복, claim ID·forbidden copy·limits 같은 내부 검증 문구, 외부 UX 활동.
- **구조 특성**: 같은 case 안에서 제품·backend·운영 근거가 함께 나타날 수 있다. 단 하나의 case를 여러 독립 성과처럼 반복하지 않는다.
- **Company AX 경계**: 현재 운영 중인 제품 Decision→release 흐름과 회사 업무 AX 확장 설계를 실선·점선으로 구분한다. MEDINESS 설계 참여·제품 운영 리드·Backend Template 직접 구축·플랫폼 구현팀의 책임을 한 표에서 분리한다.

## 4. `/portfolio/{case}` — 직접 링크 호환

- **목적**: 기존 외부 링크와 직군별 조립본이 특정 case로 직접 들어올 수 있게 한다.
- **담는 것**: 동일 case library와 claim boundary에서 파생한 문제 → 판단(대안과 근거) → 시스템 → 운영 근거.
- **담지 않는 것**: `/portfolio`와 다른 새 사실·수치·더 강한 ownership.
- **성공 기준**: **판단 줄이 있는가.** 무엇을 왜 그렇게 결정했는지 없으면 재현 가능성이 안 팔린다.
  단 **없는 판단을 지어내지 않는다** — evidence가 없으면 비워둔다 (§6·§7).
- 기본 읽기·인쇄·PDF 변환 경로는 `/portfolio` 단일 문서이며, 개별 route를 기본 탐색에 중복 노출하지 않는다.

## 5. `/chat` — 묻는 곳 (Phase 2)

- **목적**: 방문자의 질문에 **claim registry의 public 표현 범위 안에서** 답한다.
- **담지 않는 것**: registry 밖 추론. 모르면 모른다고 한다.
- 현재 상태: 입력 비활성, 데모 대화만 노출.

## 6. `/blog` · `/labs` — Phase 2

- **blog**: 생각을 공개하는 곳. **JD 리포트가 지목한 갭**(멀티에이전트 오케스트레이션·RAG)을
  실전 기록으로 덮는 자리다.
- **labs**: 만든 걸 직접 만져보게 하는 곳.
- 둘 다 현재 비어 있고 `COMING SOON`으로 표기. **의도된 상태**이며 미완성 신호를 늘리지 않는다.

## 7. 플랫폼 프로필 — 찾게 하는 곳

원티드 · 링크드인 · 리멤버 · 로켓펀치 · 그룹바이 · 사람인

- **목적**: **검색에 걸리게** 하고, 깊이는 홈으로 보낸다.
- **담는 것**: 홈페이지 문안을 각 플랫폼 제약(글자 수·필드·줄바꿈)에 맞춘 변환본 + 포트폴리오 링크.
- **담지 않는 것**: 홈에 없는 새 주장. **플랫폼에서 문안을 새로 쓰지 않는다.**
- **원칙**: 홈페이지가 SoT다. 홈 → claim 대조 → 변환본 → 플랫폼 → 실측 검증 순서
  ([content-sot](content-sot.md)).
- **주의**: 플랫폼 AI 리뷰는 **선택한 포지션 기준**으로만 판정한다. 낮게 평가하면
  ①문안이 나쁘거나 ②포지션이 목표와 다르거나 둘 중 하나다 — ②를 ①로 오독하지 않는다.

## 8. 비공개 층 — 지면이 아니지만 모든 지면을 지배한다

| 층 | 소유 | 역할 |
| --- | --- | --- |
| `wiki/evidence/` | 사실 | 무엇이 사실인가, 어디까지 확인됐나 |
| `wiki/evidence/claims/*.yaml` | 강도·표현 계약 | owned/led/co-led/contributed, `allowed_copy`·`forbidden_copy` |
| `wiki/rules/` | 작성 규칙 | persuasive-writing §1~§14, recency-weighting, public-safety |
| D2 → `app/design` | 디자인 계약 | 타입 스케일·컴포넌트 문법·레이아웃 |

**"무엇을 말할 수 있는가"는 claim registry, "어떻게 말하는가"는 홈페이지, "어떻게 보이는가"는 D2.**

## 9. 침범 판정 — 이럴 때 지면을 잘못 쓰고 있다

| 증상 | 침범 | 조치 |
| --- | --- | --- |
| 이력서의 기술 사례가 제품 소개나 연대기로 길어진다 | 기술 판정에 필요하지 않은 맥락이 섞임 | 제약·선택·구현·failure mode·검증·결과만 남기고 부가 evidence는 portfolio로 |
| 홈이 설명을 다 해버린다 | 이력서 역할을 가져옴 | 질문만 남기고 답은 아래 지면에 |
| 포트폴리오 case가 이름·기능만 나열한다 | 기술 판단 부재 | 문제·책임 범위·핵심 판단·고유한 visual·proof로 재구성 |
| Summary가 아래 섹션을 되풀이한다 | 자기 침범 | 다른 섹션이 못 하는 것만 남긴다 |
| 플랫폼에만 있는 문장이 생긴다 | SoT 이탈 | 홈에 먼저 반영하고 파생한다 |
| 사내 코드명이 노출된다 | 독자 무시 | 제품 성격으로 바꾼다 |
