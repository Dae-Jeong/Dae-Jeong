# 케이스 서술 초안 — 5단

## 01. AI 콘텐츠 생성 backend 재구축

### 검토 ✅

evidence: `thready.md:40` (User-confirmed 2026-07-19)

```
· 부분 수정 — 증상만 잡으면 의존성 구조가 그대로 남는다고 봤다. QA 티켓을 닫아도
  같은 영역에서 다른 형태로 재발하던 패턴이 그 근거였다. → 기각
· 전면 교체(FE 포함) — blast radius가 필요 이상으로 커진다. → 기각
· backend만 분리 교체 — FE(Next.js)는 유지. AI 모듈 확장이 예정돼 있어 FastAPI 분리가
  이후 확장 비용을 낮춘다고 봤다. 서비스 규모가 작은 시점이라 지금이 가장 싸다. → 채택
```

기각 근거를 함께 쓴다. `"돌아가는 기능을 왜 다시 만드나"`라는 사내 반대를
문제 누적·AI 모듈 확장·하네스 기반 이관 속도로 설득한 것도 이 칸에 들어간다.

### 검토 ✅ — 품질 판정(별도 축)

evidence: `thready.md:55` (User-confirmed 2026-07-19)

```
· 감으로 판정 — "좋은 글"의 기준 자체가 부재했다. 대표의 성공 사례도 본인 계정 n=1이라
  일반화할 수 없었다. → 기각
· LLM judge를 품질 게이트로 — 기준이 없는 상태에서 게이트를 세우면 무엇을 막는지 알 수 없다. → 기각
· LLM judge를 판단 데이터 축적 장치로 — 가설을 정량 판단으로 바꿔 데이터를 쌓고
  기준을 증명해가는 루프로 설계. → 채택
```

⚠️ **이게 이 케이스에서 가장 강한 판단이다.** judge를 "채점기"가 아니라
"기준을 발견하는 장치"로 쓴 것 — 지금 문안 어디에도 없다.

### 한계·다음 수 ⚠️

후보 (사용자 확인 필요):
- 3층 판정의 사람 판정 층은 여전히 사람 시간이 든다 — 어디까지 자동화할지 미결
- 실측 코퍼스는 "통계가 아니라 경향" — 표본 편향(검색 노출·주제·수집 방식)이 남아 있다
- **질문**: 다시 한다면 무엇을 바꾸겠나? 재구축 시점? 하네스 범위? judge 설계?

## 02. 주문·재고 비동기 처리

### 검토 ✅

evidence: `centurion.md` BAY Async (User-confirmed 2026-07-19 인터뷰)

```
· 실패 가능한 작업을 API 요청 안에서 처리 — 외부 알림·재고 연동의 지연과 실패가
  사용자 응답 경계까지 전파된다. → 기각
· 장애가 난 뒤에 분리 — 직전 회사에서 결제 실패의 불일치(선결제 예약 실패 롤백, 환불 처리
  순서, 환불 시 티켓 제거 시점)를 직접 수습해봤다. 같은 종류의 실패가 주문·재고에서도
  생긴다고 봤고, 사후 수습 비용이 훨씬 크다는 걸 경험했다. → 기각
· 제품 시작 시점부터 API 경계 밖 worker로 분리 + 재고 차감에 retry → 채택
```

**이 케이스의 핵심은 "겪어본 실패를 다음 제품에서 미리 막았다"는 것**이다.
두 회사를 잇는 서사이므로 반드시 남긴다.

### 한계·다음 수 ⚠️

- 전환(Celery → TaskIQ) 자체는 확인됐으나 **성능·지연 개선 정량은 측정값이 없다**
  (`centurion.md` Measurement boundary). 결과 칸에서 이 한계를 먼저 밝히는 게 낫다.
- **질문**: worker 분리 후 실제로 막힌 사고가 있었나? 있으면 그게 결과 칸의 강한 근거다.

## 03. 조직 표준 백엔드 템플릿

### 검토 ✅

evidence: `be-template.md` (User-confirmed 2026-07-19 인터뷰)

```
· 제품마다 각자 구조로 — 소수 백엔드 인원이 다수 제품을 담당하는 체제에서는
  제품 간 이동 비용이 그대로 병목이 된다. → 기각
· 문서 가이드만 배포 — 규약이 코드에 강제되지 않으면 제품마다 갈라진다. → 기각
· 실행 가능한 표준 템플릿 + agent context 내장 → 채택
```

⚠️ **공개 수치 주의**: 원 evidence의 "엔지니어 8명(BE 3·FE 5)이 제품 12개",
"실질 BE 2명이 12개 제품" 수치는 mediness 가드레일(internal product count 비공개)과
충돌해 **사용자 결정 대기 중**이다. 확정 전 공개 표현은
**"소수 백엔드 인원이 다수 제품을 담당하는 체제"**까지.

### 결과 — 근거 3종 ✅ (현재 문안에 일부만 반영)

evidence의 효과 3종:
1. 어떤 프로젝트든 **제품 정책만 파악하면 대응 가능** (컨텍스트 전환 비용 최소화)
2. logging·모니터링 등 **횡단 관심사를 전 제품에 일괄 반영**
3. 온보딩·FE 엔지니어도 패턴·규약·하네스 아래에서 **BE 로직 구현 가능**

→ ②③이 현재 케이스 문안에 없다. 특히 ③은 "표준이 사람을 확장한다"는 강한 근거다.

### 한계·다음 수 ⚠️

- **질문**: 템플릿이 안 맞아서 예외를 둔 제품이 있었나? 있으면 그게 정직한 한계다.

## 04. 실시간 상담 AI 세션

### 검토 ❌ — 생략

`centurion.md` SAY Realtime은 **code-backed 사실만** 있고 판단 기록이 없다
(WebSocket runtime, provider lifecycle, zombie session cleanup, reconnect race,
translation/audio pipeline). 없는 판단을 지어내지 않는다.

⚠️ **강도 주의**: `centurion.say-realtime` = **co-led**. "공동 주 기여" 표현 유지, 상향 금지.
provider 실명 비공개.

### 한계·다음 수 ⚠️

- **질문**: zombie session·reconnect race를 다루면서 "이렇게 했어야 했다" 싶은 지점이 있었나?
  있으면 그게 검토 칸을 여는 열쇠가 된다.

## 05. 제품 운영 게이트

### 검토 ❌ — 생략

`mediness.md`는 source-backed 구조 사실(pipeline registry, decision log, SPEC,
Work Package, release gate, version cut)과 tool-backed 운영 기록뿐이다. 판단 기록 없음.

### 결과 — 이미 한계를 밝히고 있다 ✅

현재 문안이 *"상태 확인 시간의 정량 변화나 에이전트의 자율 의사결정은 주장하지 않는다 —
측정하지 않았다"*로 한계를 명시한다. **5단의 `한계·다음 수`가 이미 구현된 유일한 케이스**다.

### 한계·다음 수 ⚠️

- **질문**: 게이트를 만들고 나서 실제로 막힌 릴리스가 있었나? 그 사례가 있으면
  "구조를 만들었다"가 "구조가 작동했다"로 올라간다.
