# Application Copy Standard

**이 문서는 두 가지를 막는다.** 포지셔닝이 지원본마다 흔들리는 것, 그리고 대화에서 내린 결정이 문안까지 도달하지 못하는 것.

2026-07-01~09-02 Codex 세션 304개를 검토한 결과, 정체성은 두 달간 다섯 번 바뀌었고
("Director" → Backend primary → Maker → "Tech Lead 빼자" → Maker 문장 확정),
`AI스러운 문구`·`한 줄 max 제한 금지`·`경계 문구는 구두로` 같은 결정은 각각 여러 번 반복 지시됐다.
규칙이 없어서가 아니라 규칙이 여러 문서에 흩어져 있고 문안 생성 시점에 대조되지 않았기 때문이다.

문장을 어떻게 쓰는가는 [persuasive-writing](persuasive-writing.md)이, 사실·강도는
[evidence-policy](evidence-policy.md)가, 공개 범위는 [public-safety](public-safety.md)가 계속 소유한다.
이 문서는 그 위에서 **무엇을 고정하고, 무엇을 회사별로 바꾸고, 제출 전에 무엇을 대조하는가**만 소유한다.

## 1. 고정 — 회사별 작업에서 건드리지 않는 것

아래 네 가지를 바꾸려면 공통 이력서에서 먼저 바꾸고, 분기에 한 번만 검토한다.
회사별 지원본을 만드는 도중에 이 층을 고치지 않는다.

### 1-1. 정체성 층

| 층 | 값 | 어디에 쓰는가 |
| --- | --- | --- |
| 브랜드 문장 | `가능성을 기회로 바꾸고, 제품으로 가치를 전하는 메이커 김대정입니다.` | 홈 hero, 공통 이력서·포트폴리오 소개 |
| **회사별 소개 첫 줄** | 위 브랜드 문장 그대로. 둘째 문단은 `기획자로 시작해 백엔드로 왔고, …` 뒤에 실제 제품·기여를 구체적으로 잇는다 | §1-6 브랜딩 문장·경력기술서 첫 줄 규칙을 따른다. 폐기된 확장형·추상 소개·별도 보조 헤드라인을 되살리지 않는다 |
| 채용 역할 (공통) | `Tech Lead · Backend Engineer` | 공통 이력서 헤더 |
| 채용 역할 (회사별) | **공고의 직무명을 그대로** + 근거 있는 보조 역할 | 회사별 헤더. 예: `Backend Engineer · Tech Lead`, `Software Engineer / AI · Backend Engineer`. §1-6 역할 표기를 따른다 |
| 전문 영역 | `AI Product Systems` | 공통·회사별 동일 |

- 회사별 헤더의 직함은 그 공고가 필요로 하는 직군 명칭에 맞춘다 (2026-09-02 user-confirmed). `Tech Lead`를 앞에 두는 것은 리드 포지션 공고뿐이다. 2~5년 백엔드 공고에서 Tech Lead가 앞에 오면 28개월 backend 경력과 대조돼 부풀리기로 읽힌다.
- 브랜드 문장은 공통·회사별 모두 소개 첫 줄에 그대로 둔다. 확장형은 폐기됐으며, 둘째 문단이 1-2의 세 사실을 구체적으로 설명한다. owner: [identity.md](../profile/identity.md)의 확장형 폐기 결정. 2026-09-07 독립 검토에서 발견한 잔존 지침을 §1-6·게이트 16과 정합화했다.
- 정체성의 canonical owner는 [profile/identity.md](../profile/identity.md), 역할 전달 방식은 [role-positioning-standard](../products/resume/role-positioning-standard.md)다. 이 표는 회사별 적용 규칙만 더한다.
- 공용 영문 CV는 같은 문장의 [English 정본](../profile/identity.md#english)을 사용한다. 번역은 별도 브랜드 생성이 아니며, Jake 양식에서는 문서 종류 대신 영문 이름을 제목에 둔다 (§1-6 공용 영문 CV 양식). 한국어 문서·회사별 제목은 기존 규칙을 유지한다.

### 1-2. 15초 문장 — 세 사실

어느 지원본이든 소개에 아래 세 사실이 **순서만 바뀌어** 들어간다. 하나라도 빠지면 게이트 2 위반이다.

1. **기획자 출신 백엔드 엔지니어** — PM을 실제로 1년 했고, 그 경험이 backend 판단에 쓰인다. 고정 브랜드 문장 뒤에서 `기획자로 시작해 백엔드로 왔고, …`로 시작해 실제 제품과 직접 기여를 설명한다.
2. **아이디어를 제안해 실제 결제 고객이 있는 AI 제품으로 만들고 직접 구현·운영** — backend·AI·핵심 frontend 직접 구현.
3. **AI 활용이 본격화되면서 모두가 메이커로 제품을 만들고 운영하는 팀에서, 백엔드 경험이 적은 팀원도 같은 기준으로 만들 수 있는 조직 표준과 agent 작업 기준을 직접 구축** — Template 효과까지. 2026-09-03 user-confirmed: `백엔드 2~3명이 다수 제품을 맡는` 인원 부족 서사는 쓰지 않는다. 표준의 이유는 인원 수가 아니라 모두가 메이커가 된 팀 구조다.

세 사실의 문안 원형은 [resume-block-library](../products/resume/resume-block-library.md)의 `intro.*` 블록이 소유한다.

### 1-5. 기술 주장의 축 (2026-09-03)

기술적으로 어필하는 축은 **성능·보장·신뢰·멱등·정합·설계** 여섯 개다. owner는 [profile/engineering-keywords.md](../profile/engineering-keywords.md). 이 축은 기술 근거를 고르는 참고 분류이지 제목의 단어 할당량이 아니다. 제품·시장 성과를 먼저 읽히게 하고, 관련 기술 판단은 해당 성과의 본문에서 구체적으로 설명한다. 대표 성과 수나 제목에 들어갈 기술 단어 수를 강제하지 않는다 (2026-09-07 사용자 성과 위계 결정, §1-6·게이트 25).

### 1-3. 대표 성과 풀

회사별로는 이 풀에서 3~5개를 고르고 순서만 바꾼다. **회사별 작업 중에 새 성과를 만들지 않는다.**
새 성과가 필요하면 evidence → claim → block library 순서로 먼저 올린다.

| ID | 성과 | 결과 문장의 핵심 |
| --- | --- | --- |
| A | Thready 고객 진입 장벽 해소·제품화 | 채널 운영의 시간·경험 부족을 생성·승인·발행 흐름으로 해결, backend·AI·핵심 frontend 직접 구현 |
| B | API 계약을 유지한 backend 병렬 재구축 | 대안 비교 → 도메인·트랜잭션 경계 설계 → 응답 검증 → 전환·운영 |
| C | 주문·재고 비동기 처리 | Celery→TaskIQ 판단, 작업 상태·실패 기록·수동 재처리 경계. 자동 재시도 수렴은 미확인 |
| D | AI 서비스 분리·Outbox | 원장/실행 분리, STG 이관 검증, delivery fence |
| E | Backend Template 효과 | STG session·pool 오류 재발 없음, 비개발 직군이 제품 구현, BE 개입 축소 |
| F | NEXUS multi-tenant backend | gateway·admin·homepage 분리, server-owned 지점 권한 |

블록 문안·강도·허용 수치는 [resume-block-library](../products/resume/resume-block-library.md)가, 문서별 포함 깊이는 [common-content-inventory.yaml](../products/resume/common-content-inventory.yaml)이 소유한다.

### 1-4. 수치 정책

수치는 claim의 `allowed_copy`가 상한이다. 이 표는 그중 **공개 지원본에서 실제로 쓰는 것과 쓰지 않는 것**을 한 곳에 모은다.

| 구분 | 항목 | 규칙 |
| --- | --- | --- |
| 쓰지 않는다 | QA reopen `37% → 11%` (또는 `26%p`) | 2026-09-08 사용자 결정. 초기 baseline에 좌우되는 비교이므로 현행 성과에서 제외한다. 측정 기록·frozen 제출본은 보존 |
| 쓰지 않는다 | STG 이관 `2,616 · 795 · 7,111` | 2026-09-03부터 수치 대신 절차(parent→child 순서 streaming copy, 영구 cross-DB link 없음)로 서술한다. 내부 규모 수치는 도식 공개 수준(2-1)과 같은 이유로 뺀다 |
| 쓴다 | 팀 성격 `AI 활용이 본격화되며 모두가 메이커로 제품 개발·운영에 참여` | Template 효과의 맥락으로만. 인원 수(`백엔드 2~3명`)로 표준의 이유를 설명하지 않는다 (2026-09-03) |
| 쓴다 | 특허 등록 `10-2898273`, CES 2024, KCL 통과 | Credentials 섹션. 출원번호는 쓰지 않는다 |
| 조건부 | corpus `13.1만 행 · 318만 관측` | 데이터 JD일 때 **두 개까지**. 11.1만·18.5만·4,039·20,256을 같이 나열하지 않는다 |
| 조건부 | 작업 시간 `36시간` | 검증 하네스와 병기할 때만. 단독 사용 금지. AI 시대에 속도 자체는 신호가 약하다 |
| 쓰지 않는다 | HTTP 5xx 0.3%, 월 수만 건 | baseline이 없고 규모가 작게 읽힌다. 재측정 전 제외 |
| 선택·보조 근거 | `월 1천만원 수준의 구독 매출이 발생하는 제품` | 공개 가능한 상한은 유지하되 2026-09-08 사용자 결정으로 첫 성과·제목의 필수 강조에서 제외한다. 고객 문제를 해소한 제품 기능과 직접 엔지니어링 기여를 먼저 쓰고, 매출은 유료 수요를 확인한 보조 결과로 사용한다. 인접 본문에 2026년 8월 기준과 팀 outcome을 명시한다. 정확 금액·MRR·연 환산(`연 1억`)·월평균·지속 성장·개인 인과는 계속 금지 (§4 게이트 25 사람 검사) |
| 조건부·고객 사례 | `기존 대비 팔로워 10배 이상 증가` | claim `thready.customer-follower-growth`의 실제 고객 한 사례로만 쓴다. 꾸준한 서비스 활용과 채널 운영의 결과이며, 특정 기능의 인과·전체 고객 평균·측정 기간·시작/종료 팔로워 수는 확정하지 않는다 (§4 게이트 25 사람 검사) |
| 쓰지 않는다 | UX 컨설팅 DAU 200%·순위 9→5 | confidence medium, 공유받은 수치. `순위·DAU 상승에 기여`까지 |
| 쓰지 않는다 | 커밋 수·blame 비율 | 내부 근거. 공개 문안에서는 강도 동사로만 |
| 쓰지 않는다 | 6축 점수, Yolo 정확도, TellingMe 규모 | 기존 금지 유지 |
| 쓰지 않는다 | 내부 토폴로지 수치 (`6개 root · 400개 state`, `10대 VM · 알림 8개`, VAD ms 파라미터, `모델 추론 약 80%`) | 2-1과 같은 기준. `제품군·환경별 root/state로 변경 범위 격리`처럼 구조로 쓴다 |
| 쓰지 않는다 | 결함 재발 `약 94% 감소(하루 4.5건 → 0.3건)` | QA reopen과 연결된 초기 baseline 비교이므로 현행 성과에서 함께 제외한다. 정성적 `재발 대폭 감소`로 우회하지 않는다 |

### 1-6. 표현 고정 (2026-09-03)

회사별 지원본을 전수 검토하며 확정한 표현 규칙. 위반 예는 그날 실제로 고친 문장이다.

| 항목 | 규칙 | 고친 예 |
| --- | --- | --- |
| 공용 영문 CV 양식 | 공용 CV는 해외 지원용 영어로 작성하고 사용자 지정 Jake’s Resume를 적용한다. 이름 중심 헤더·흑백 단일 컬럼·경력 우선·기간 우측 정렬을 사용한다. 브랜드 문장은 `profile/identity.md`의 English 정본을 쓰며 한국어 본문·표제나 임의의 다른 템플릿을 섞지 않는다. 전체 이력·기여 강도는 보존하고 한 쪽을 맞추려 경력을 삭제하지 않는다. 다른 3종과 회사별·frozen 패키지는 유지한다 (2026-09-08 user-confirmed) | CV를 한국어 자체 UI로 생성, Harvard 양식으로 임의 대체 → 영문 Jake 양식, 경력 우선, 같은 app 문안에서 웹·LaTeX 파생 |
| 템플릿 출처의 위치 | CV 화면에 양식 제작자 안내 영역을 붙이지 않는다. 출처는 소스 주석·패키지 계약에 두고 MIT 저작권·허가 고지는 원본 LICENSE로 보존한다 (2026-09-08 user-confirmed) | CV 끝에 `Layout adapted from…` 안내와 구분선 → 화면에서 제외, 출처·라이선스는 저장소에 유지 |
| Thready QA 감소율 비선택 | 인계 후 QA 개선 서사와 재오픈·재발 감소 수치는 현행 공용·mutable 지원본에서 제외한다. 재구축은 보호한 API 계약·도메인/트랜잭션 경계·응답 검증·전환 책임으로 쓴다. 측정 근거와 frozen 제출본은 보존하고 채용 플랫폼은 명시적 동기화 요청 전에는 수정하지 않는다 (2026-09-08, 게이트 33) | `재구축 뒤 결함 재발 약 94% 감소` → `API 계약을 유지한 백엔드 재설계·전환` |
| Thready 제품 시작 서사 | 공개 문안은 아이디어 제안·제품화·직접 개발·출시·운영을 중심으로 쓰고 `인계받은`·`초기 프로토타입 이후`를 도입부에 반복하지 않는다. 재구축은 보호한 API 계약·대안·검증·전환 판단으로 설명한다. 최초 prototype 작성 이력은 evidence에 보존하며 `처음부터 전부 직접 구현`으로 바꾸지 않는다 (2026-09-08, 게이트 32) | `인계받은 Thready 백엔드` → `Thready 백엔드를 기존 API 계약을 유지하며 병렬 재구축`. `초기 프로토타입 이후 제품화` → `아이디어 제안부터 제품화·출시·운영까지 주도` |

### 1-7. 기술 표의 분류 기준

**기술 표는 무엇을 사용하는지 빠르게 찾는 곳이고, 성과·경력기술서·포트폴리오는 그것으로 무엇을 해결했는지 보여주는 곳이다.** 아래는 공식 산업 표준이나 고정 양식이 아니라, 2026-09-07 사용자 결정으로 채택한 이 workspace의 기본 편집 기준이다.

2026-09-07 후속 사용자 결정: **분류의 완전성보다 간결한 읽기를 우선한다.** 아래 세부 분류는 배치 참고표이며, 화면에서 전부 독립 행으로 만들지 않는다. JYP v2는 `Backend / AI·LLM / Frontend / Engineering Tools` 네 범주로 묶는다. 언어·DB를 관련 구현 영역으로, 개발·검증·배포·모니터링 도구를 Engineering Tools로 병합할 수 있다. 사례와 반복되는 행별 활용 설명은 생략하고 필요한 설명만 짧게 둔다. 보조 경험은 근거가 확인된 `추가 기술` 한 줄로 표시할 수 있다. 네 범주 역시 모든 문서에 강제하는 개수는 아니다.

| 기본 분류 | 배치 예 |
| --- | --- |
| Languages | Python · TypeScript |
| Backend | FastAPI · SQLAlchemy · Celery |
| Frontend | Next.js |
| Databases & Cache | PostgreSQL · MySQL · Redis |
| AI / LLM | LangGraph · LLM 연동·평가 |
| Infrastructure & Delivery | Docker · GitHub Actions |
| Development & Quality | Claude Code · Codex · pytest · Ruff · Pyright |
| Monitoring & Collaboration | Sentry · Jira |

- 이 표는 **분류 예시이지 모든 지원본에 포함할 기술 목록이 아니다.** 실제 기재 항목과 사용 범위는 profile/evidence에서 선택한다. 분류명이 Frontend나 Infrastructure라고 해서 전문성·기여 범위를 상향하지 않는다.
- 필요한 분류만 사용하고, 관련 항목이 적으면 의미가 가까운 분류끼리 묶는다. 제목 언어는 문서 안에서 일관되게 사용하며, 같은 도구를 여러 행에 반복해 분량을 늘리지 않는다. 강점과 JD에 따라 순서를 바꾼다.
- `제품 화면` 같은 결과물이나 `데이터 전달` 같은 특정 처리 문제를 새 기술 범주로 삼지 않는다. 위 분류에서 수용할 수 없는 기술은 포함 항목들의 공통 성격을 설명할 수 있을 때만 새 범주를 검토한다.
- Outbox 같은 개별 설계 패턴은 독립 범주로 승격하지 않는다. 기술 설명에 필요한 경우 해당 분야의 활용 설명에 넣거나 구현 사례로 옮긴다. `typed prompt·structured output`도 이 문서에서는 AI 활용 설명으로 다룬다. 설계 개념을 기술 역량에서 전면 금지한다는 뜻은 아니다.
- Stripe 같은 서비스 연동은 관련 경험의 기술 스택·구현 설명에 둔다. 같은 `외부 도구`라는 이유로 결제 서비스·작업 큐·배포 도구를 `운영·협업` 한 행에 모으지 않는다.
- 원문을 웹으로 내보낼 때도 분류만 기계적으로 복사하지 않고 게이트 22를 확인한다. 사실·claim은 유지하고 문안 owner와 typed content의 분류를 함께 맞춘다. frozen 제출본은 소급 수정하지 않는다.

참고: [University of Rhode Island의 CS 이력서 안내](https://career.uri.edu/resources/resume-sample-computer-science-2/)는 언어·프레임워크/라이브러리·개발 도구·클라우드·데이터베이스·AI 등을 기술 영역으로 안내한다. 구체적인 위 분류와 배치 원칙은 이를 참고한 우리의 편집 결정이다.

## 2. 포장 — 허용되는 범위

**포장은 선택·순서·프레임이지 사실의 변경이 아니다.** 아래는 허용되는 포장이다.

- **지원자에게 가장 유리한 강점을 먼저 배치한다.** JD의 핵심 기대와 기존 성과를 비교해 선택받을 이유를 정한다. 질문 수·항목별 일대일 대응·전 항목 충족을 목표로 삼지 않으며, 관련성이 약한 항목은 공개 문안에서 생략할 수 있다.
- **우려에 대한 선제 답변은 선택이다.** 회사의 우려를 임의로 만들어 소개에 방어 문장을 넣지 않는다. 확인된 중요한 선택 조건이 있고 이를 설명하는 것이 지원자에게 유리할 때만 다룬다. 도메인 전환 경험도 부족함의 해명보다 반복해서 발휘한 강점으로 쓴다.
- **강도를 낮춰 쓰지 않는다.** `owned`인 일을 "참여했습니다"로 쓰는 것도 부정확이다 ([persuasive-writing §4](persuasive-writing.md)). 회사 AX 설계 `참여`와 Template `직접 구축`은 같은 문장에서 동사를 분리한다.
- **결과 또는 판단으로 문장을 끝낸다.** 범위 한정은 문장 **중간**에 둔다.
- **재구축은 판단 서사로 쓴다.** 행위가 아니라 대안·시점·검증·위험 미현실화의 리스크 통제 증거다 ([persuasive-writing §11](persuasive-writing.md)).
- **AI 활용은 도구명과 경계로 쓴다.** `Claude Code·Codex를 codebase 분석·기능 inventory·반복 구현·검증에 활용, architecture·test·release 판단은 직접 소유`가 허용 문안이다. "AI로 폭발적 퍼포먼스" 같은 형용사는 쓰지 않고, 1년 6개월 동안 맡은 제품·시스템의 **목록**이 그 말을 대신한다.

### 2-1. 도식 공개 수준 (2026-09-03)

도식은 **패턴 수준**까지 공개한다. 역할·경계·순서·실패 분기·불변 조건·버린 대안·검증 방법은 그린다. 다음은 그리지 않는다.

- 내부 식별자: 함수·노드·헤더·API 경로·큐 제품·외부 채널·provider·모델 실명. `input_guard`는 `소재 유무 판정`으로, `X-Branch-Id`는 `지점 id 헤더`로 쓴다.
- 정확한 수치: 재시도 횟수·간격·초·건수·성공률. 구조를 설명하는 데 필요하면 `상한 N회`, `고정 간격`처럼 관계만 남긴다. 검증 근거 줄에는 "무엇으로 정했다"까지만 쓴다.
- 실제 topology 구성: 어느 root에 무엇이 몇 개, 제품군 구성, 전결 매트릭스. `공통 root / 제품군 root × N / 환경별 state`처럼 경계 구조만 남긴다.

추상화·강조는 허용이고 변형은 위반이다. 없던 구조를 있는 것처럼, 팀 결정을 내 결정처럼, 우회책을 근본 해결처럼 그리지 않는다. 구현/설계가 섞인 도식은 요소마다 `구현`·`설계` 표식을 둔다. 도식 자산의 SoT는 [Design Diagram Library](../products/portfolio/design-diagram-library.md)다.

아래는 포장이 아니라 위반이다.

- 포트폴리오 hero에 보조 줄·헤드라인·문단 3단을 두는 것, 목차를 hero 오른쪽과 본문에 두 번 두는 것, 케이스·목차에 `local 적재 검증`·`STG 검증`·`Prototype` 같은 상태 라벨과 `A → B`식 화살표 제목·mono 글꼴 메모 말투를 쓰는 것 (2026-09-03 user-confirmed). 정직함은 케이스 본문의 담당 범위·검증 범위 문단이 맡는다.
- 경계 문구를 이력서 본문에 남기는 것. `범위 밖`, `미측정`, `production 배포 아님`은 claim과 면접 답변에 둔다. 2026-08-31 user-confirmed: "이력서에서 이 내용은 제거하자, 이거는 내가 구두로 전달할게".
- 내부 용어를 외부 독자에게 그대로 노출하는 것. `Decision·SPEC·Work Package·human gate·agent-readable`은 `결정·명세·작업 기록`, `사람 승인 경계`로 바꾼다.
- 영문 명사를 조합한 번역투. `SNS data·AI 품질 system`, `release·production operation` → 한국어로 바로 읽히게 ([persuasive-writing §9](persuasive-writing.md)).
- 프레임워크명을 전문성처럼 반복하는 것. `Next.js`는 기술 섹션 stack 줄에만 두고 산문에서는 `핵심 화면 직접 구현`으로 쓴다 (2026-09-03 user-confirmed — 화면을 만든 사실은 맞지만 FE 전문가로 읽히면 부정확).
- 사실을 바꾸거나, 금지 수치를 쓰거나, 동사 강도 상한을 넘는 것. 하드 제약은 이 셋뿐이다. 후킹·제목·첫 문장·칸의 순서와 길이는 자유이며, 블록은 기본값이지 원형 강제가 아니다.

## 3. 회사별 조립 절차

[tailor-resume skill](../../skills/tailor-resume/SKILL.md)의 workflow 안에서, 문안 단계는 아래 순서로만 진행한다.

1. JD의 핵심 기대를 파악하고 기존 성과 중 지원자에게 가장 유리한 선택 이유를 정한다 (`match-report.md`). 전 항목 대응은 내부 분석과 공개 문안 모두의 완성 조건이 아니다.
2. 그 선택 이유를 가장 잘 보여주는 성과 풀(1-3)의 블록을 골라 첫 페이지 순서와 비중을 정한다. 질문 하나당 블록 하나를 강제하지 않는다.
3. 추가 맥락이 설득력을 높일 때만 소개에 더한다. 추정한 회사 우려·부족한 경험·면접 방어 문구는 자동으로 넣지 않는다.
