# Content Rules — 이력서에 무엇을 담는가

이력서는 **정적 프레임**이다. 섹션 구성과 분량은 고정하고, JD 맞춤은 "무엇을 고르고 어떤 순서로 놓는가"로만 한다.

역할 분담 (2026-07-05 user 확정):

> 이력서는 채용 담당자를 hooking해서 포트폴리오로 넘기는 문서다. 자세한 내용은 포트폴리오가 담는다.

## 이력서 vs 포트폴리오

| | 이력서 | 포트폴리오 (홈페이지/케이스 스터디) |
| --- | --- | --- |
| 목적 | 15초 안에 적합성 판단 → 다음 단계로 hooking | 깊이 검증 — "정말 했는가, 어떻게 했는가" |
| 담는 것 | 무엇을(시스템/도메인) + 어떤 역할로(전담/주도/공동) + 어떤 기술로 | 왜/어떻게 — 문제 -> 접근 -> 구현 -> 운영 서사 |
| 형식 | 한 줄 bullet | 아키텍처 결정, 트레이드오프, 다이어그램, 수치/벤치마크, 코드 수준 디테일 |
| 예 | "backend를 FastAPI 기반으로 전면 재구축(v1.1.0 cutover)하고 개발·운영 전담" | 왜 재구축했나, cutover 전략, DDD 계층 설계, 전환 중 리스크 관리 |

**판정 기준**: bullet을 읽고 "더 궁금해지면" 성공이다. 궁금증을 이력서 안에서 해소하려고 설명을 붙이기 시작하면 그 내용은 포트폴리오로 보낸다.

## 정적 프레임 — 2구역 구조 (2026-07-05 user 확정)

경력직 이력서는 두 구역으로 명확히 분리한다:

- **A구역 — 무엇을 할 수 있는가**: 경력직 어필의 본체. 회사 업무/개인 프로젝트 구분 없이 "할 수 있는 것"의 근거를 담는다.
- **B구역 — 어떤 사람인가**: 일하는 방식, 학력, 기타 특징. A구역을 통과한 독자가 보는 보조 정보.

핵심 원칙 (2026-07-06 user 확정): **경력 섹션은 프로젝트 소개가 아니다.** 능력은 02에서 기술/역량 기준으로 묶어 서술하고, 프로젝트는 그 근거 태그로만 등장한다. 프로젝트 자체가 어필이 되는 경우에만 04에 독립시킨다.

| 구역 | # | 섹션 | 고정 규칙 | JD 맞춤 허용 범위 |
| --- | --- | --- | --- | --- |
| — | — | 헤더 | 이름/연락처 고정 | role-line, tagline 문구만 |
| A | 01 | 요약 | **3~4줄 고정** | 문구 재작성 (JD 핵심 요구 2~3개 대응) |
| A | 02 | 핵심 역량 | **기술/역량 기준 그룹 5~6개 고정** — 그룹당 [할 수 있는 것 선언 1줄 + 근거 1줄(프로젝트 태그, 회사/개인 무관)] | 그룹 순서 재배열 + 근거 선별 |
| A | 03 | 기술 | **4행 고정** (Language/FW, Data/Messaging, Infra, AI) | 행 내부 나열 순서만 |
| A | 04 | 대표 프로젝트 | **그 자체로 어필되는 것만 최대 3개**, 각 bullet 1~2개. 해당 없으면 섹션 생략 | 프로젝트 선택 |
| A | 05 | 경력 | **컴팩트 타임라인** — 회사 4(메디솔브/메멘토/스튜디오랩/아이즈솔) + 개인 1(TellingMe), 시간 역순. 항목당 회사/역할/기간 + 한 줄 요약. 상세 bullet 금지 (역량 근거는 02 담당) | 한 줄 요약 문구 |
| B | 06 | 일하는 방식 (Agent Workflow) | 유지 또는 삭제 — **두 상태만** (부분 수정 없음) | 유지/삭제 선택 |
| B | 07 | 학력 · 교육 | 고정 (FIXED) | 없음 |
| B | 08 | 수상 · 특허 · 자격 | 고정 (FIXED) | 없음 |

분량 결과: 이 프레임을 지키면 자동으로 A4 1~1.5장이 된다. 분량을 줄이려 규칙을 어기지 말고, 규칙을 지켜 분량이 나오게 한다.

## 문체 규칙 (2026-07-06 웹 리서치 기반)

- **전 영역 개조식** — 명사형 종결("~구축", "~설계·운영", "~전담"). "~합니다" 문장체 금지. 줄글 문단 금지.
- **수사 금지** — "감이 아니라 시스템으로", "~까지 가져갑니다" 같은 마케팅 표현 대신 사실 서술.
- **XYZ 변형 구조** — [행위+대상(명사형)] + [방법/기술] + [검증 가능한 규모·사실]. 수치는 09에 등재된 검증 값만 (수치 창조 금지 — 가드레일이 컨벤션보다 우선).
- **tagline** — "N년차 백엔드 엔지니어 | 핵심 키워드 2~3개" 패턴.
- 예외: 푸터 서명 문장은 유지.

## Bullet 작성 형식

```
[시스템/도메인] + [무엇을 했다(역할 강도)] + [핵심 기술 1~3개]
```

- 배경 설명, 문제 정의, "~하기 위해" 같은 사유 서술 금지 — 전부 포트폴리오 몫.
- 역할 강도는 claim strength 표(09) 상한 준수: 전담/주도/공동/참여.
- 수치는 로그/벤치마크 근거가 09에 등재된 것만.

## 포트폴리오로 보내는 것 (이력서 금지 목록)

- 문제 배경과 의사결정 과정 (왜 그 구조를 택했나)
- 아키텍처 다이어그램, 화면, 코드
- 2문장 이상 필요한 모든 설명
- 세부 작업 나열 (work log 수준의 항목들)
- Agent Workflow의 구체 artifacts 상세 — 이력서에는 4줄 요약까지만
