# Render Server Architecture

## Owner와 적용 범위

서버·배치 구성도의 생성·검토 workflow다. 글로벌 시각 선호를 이 파일에 복제하지 않는다.

1. 머신의 agent entry가 안내하는 글로벌 wiki에서 `wiki:meta/agents/collaboration#Server Architecture Views`를 읽는다. 실제 경로는 entry를 통해 해결하며 이 portable skill에 PC 경로를 고정하지 않는다. 정본에 접근할 수 없으면 이를 알리고 현재 사용자가 제공한 표현 요구를 적용한다.
2. 질문이 배치·연결 구조인지 확인한다. 시간 순서, 상태 전이, ERD, 수치 차트라면 이 스킬로 표현을 강제하지 않고 해당 질문에 맞는 표기법을 선택한다.
3. 기존 도식을 수정한다면 현재 원본과 PC 렌더를 먼저 확인한다. 참고 예시는 `workspace:laughtale/tasks/linky-chat-overview.html`이며 사용 가능할 때만 읽는다. 프로젝트 사실·스택의 source로 사용하지 않는다.

## 입력과 사실 경계

- 현재 코드·배포 설정·승인된 설계에서 구성요소, 연결 방향, 통신 종류, 경계 소속, 복제 의미를 추출한다. 실제 구현·후보·미구현·미확인을 분리한다.
- Dae-Jeong의 공개 포트폴리오라면 [공개 도식 범위](../../../wiki/rules/application-copy-standard.md#2-1-도식-공개-수준-2026-09-03)와 해당 claim을 먼저 확인한다. 실제 내부 topology 대신 공개 가능한 패턴으로 추상화한다. 이 과정에서 미구현을 구현으로 바꾸지 않는다.
- 구성도 요청은 서비스 구현, 인프라 변경, 클라우드 선택, 외부 게시 권한이 아니다.

## 제작 흐름

### 1. 사실과 표현 재료

1. 먼저 근거에서 `구성요소 → 실행 환경/소유 경계 → 연결 대상·프로토콜 → 구현 상태`를 정리한다. 사실 source와 표현 reference를 섞지 않는다.
2. 사용자가 준 아키텍처 예시를 실제로 열어 정본의 수용 기준과 비교한다. 기존 자산은 [공식 Azure 아이콘](../../../app/fe/public/azure/)에서 재사용할 수 있다. 해당 서비스와 일치하는 아이콘만 사용하고, 원형·색·비율을 임의로 변형하지 않는다. 라이선스·사용 조건은 [공식 출처](https://learn.microsoft.com/en-us/azure/architecture/icons/)에서 확인한다.

### 2. 공간 배치와 연결

- **구조 먼저:** 이 그림이 설명할 관계를 선택하고 관련 노드를 묶는다. 예를 들어 소유 경계가 주제라면 `제품 API + 제품 DB`, `AI + AI DB`를 각각 놓은 뒤 경계를 감싼다. 서버 행·DB 행 같은 고정 틀부터 만들지 않는다. 네트워크 배치가 주제라면 검증된 네트워크 경계가 우선이다.
- 그룹의 내용과 제목을 놓고 경계 크기를 맞춘 다음, 그룹 사이에 공통 의존성·분기점·연결 통로를 배치한다. 비어 보인다고 설명이나 노드를 더하지 않는다. 글로벌 정본의 relationship-first layout 기준으로 구조를 판정한다.
- 아이콘만 먼저 놓지 말고 `아이콘 + 이름 + 보조 라벨`의 전체 점유 영역을 잡는다. 그룹 제목 자리와 연결선 통로를 예약한 후 노드를 정렬하고 경로를 그린다. 배치의 시각적 기준은 글로벌 정본의 spacing refinement를 따른다.
- 주요 요청 경로를 먼저 읽히게 하고 배포·관측 경로를 별도 통로로 연결한다. 배포·관측 관계의 연결 대상이 없거나, 논리 그룹이 실제 네트워크로 오독되면 완성이 아니다.
- 막히는 곳은 노드·그룹·통로를 재배치한다. 텍스트를 줄이거나 그림 전체를 축소해 충돌만 숨기는 수정은 피한다. 다른 영역의 빈 공간도 함께 검토한다.

### 3. 실제 크기 검수

- **디테일은 별도 패스:** 구조가 읽힌 뒤 연결 anchor와 라벨 기준선을 점검한다. 가능하면 아이콘 중심·입출력 anchor를 공통 좌표에서 계산해 선마다 좌표를 따로 맞추지 않는다. `Client → API → AI` 같은 수평 관통 경로는 좌우 선의 y와 라벨 높이를 비교하고, 수직 경로는 x를 비교한다. 의도적인 꺾임은 이유가 읽히는지 확인한다.
- 아이콘 로딩과 원형 유지, 선의 시작·끝, 라벨 교차, 경계 포함 관계를 확인한다. 노드끼리뿐 아니라 그룹 제목·가장자리와의 간격도 본다.
- 대표 PC viewport에서 스크린샷을 reference 및 수정 전 화면과 대조한다. `동급 아이콘·라벨 정렬 / 그룹 안쪽 여백 / 선·라벨 여유 / 전체 시각 중심`이 개선됐는지 보고한다. overflow 없음은 필요조건이지 수용 판정이 아니다.
- A4는 요청된 경우 실제 출력으로 별도 검증한다. 화면 검증만 했다면 PDF까지 검증했다고 보고하지 않는다.

### 4. 산출물과 범위

- 정본의 표현 기준을 적용해 기존 자산 또는 code-native HTML/SVG로 만든다. 번들 skill cache는 수정하지 않는다. 단순한 배치도에 불필요한 인터랙션이나 새 라이브러리를 추가하지 않는다.
- 산출물은 해당 작업의 실제 파일로 저장한다. 이 repo의 공개용 도식 owner는 [Design Diagram Library](../../../wiki/products/portfolio/design-diagram-library.md)이며 검토 산출물과 승인된 공개 자산을 구분한다.
- Orca에서는 사용 가능한 `orca-cli` skill의 현재 가이드로 파일/로컬 URL을 열고, 정본의 PC 렌더 기준을 검사한다. A4가 요구되면 인쇄 방향과 실제 크기를 별도 검증한다.
- 반환 시 파일 또는 실제 로컬 화면을 링크하고 검사한 viewport·남은 미확인 사항을 보고한다. 렌더할 수 없으면 완료로 포장하지 않고 미검증으로 남긴다.
