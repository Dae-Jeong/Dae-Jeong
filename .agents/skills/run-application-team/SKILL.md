# Run Application Team

지원자가 회사를 선택하고 자신의 근거를 전달하도록 돕는 협업 workflow다. 실제 채용 담당자·채용 매니저·면접관·기술문서 작성자의 방식을 차용하되, 해당 기업의 채용위원회인 것처럼 판단하거나 합격을 예측하지 않는다.

처음 팀을 구성하거나 역할을 바꿀 때 [실무 방식과 차용 경계](references/practitioner-methods.md)를 읽는다. 각 역할에 적용한 방법을 사용자에게 짧게 설명한다. 세 팀과 조정자 구성은 우리의 설계이며, 특정 실무자의 조직을 그대로 재현한 것이 아니다.

## 1. 의뢰 범위부터 정한다

- `스킬/팀 설계 먼저`라면 실제 회사 조사·지원 문안 작업을 시작하거나 재개하지 않는다. 설계 산출물과 검증까지만 한다.
- `회사·JD 재분석`은 분석과 작성 방향까지만, `문안 작성/수정`은 요청한 Markdown 초안까지만 수행한다. 팀 구성 요청 자체는 파일 저장·승인본 교체·PDF 생성·지원 제출 권한이 아니다.
- 대상은 사용자 지정 회사 × 직무 × 지원 경로로 식별한다. `아직 지원 전`이면 [지원 원장](../../../wiki/products/resume/application-registry.yaml)의 `pre-apply`만 선택한다. 최신 정정·로그인 화면·동결 보호는 [lifecycle](../../../wiki/products/resume/application-lifecycle.md)을 따른다.
- 조정자가 대상, 이번 산출물, 쓰기 허용 파일, 종료 지점, 남은 사용자 선택을 짧은 kickoff brief로 공유한다. 스킬의 기본 단계가 사용자의 명시적 요청 범위를 좁히거나 넓히지 않도록 한다.

## 2. 최소 팀을 실제로 구성한다

**먼저 이미 돌고 있는 실행자를 확인한다.** Orca에 해당 workspace의 세션이 열려 있으면 그 세션을 재사용하고, 새 agent·Run을 자동으로 만들지 않는다. 새 실행자가 필요하면 무엇이 왜 필요한지 사용자에게 올려 승인을 받는다. **이미 대화에서 실행자 구성이나 재사용을 승인받았으면 다시 묻지 않는다.**

재사용할 실행자가 있고 동시 실행이 가능하면 조정자(main) + 분석·작성·검토 담당으로 구성한다. 동시 슬롯과 독립 작업량에 맞춰 조정하고, 회사마다 팀 전체를 복제하지 않는다. 순차 역할 수행으로 대체했다면 독립 다중 에이전트 검토라고 보고하지 않는다.

| 담당 | 맡는 판단과 결과물 | 다른 팀에 되돌리는 것 |
| --- | --- | --- |
| 분석 | 회사의 고객·제품·사업 맥락, 현재 JD의 결과 기대·필수/우대 조건, 요구↔claim 매핑 → 근거가 붙은 분석 brief | 회사/요건의 불명확함은 확인 질문으로, 표현상 필요한 추가 증거는 작성팀과 협의 |
| 작성 | 독자에게 먼저 전달할 관련 경험·순서·인과 구조 → 작성 brief 또는 허용된 초안 | 증명할 수 없는 주장은 분석팀에 근거 요청. 사실·연차·기여 강도를 문장으로 메우지 않음 |
| 검토 | 원문·개인 근거에 대한 독립 1차 판단, 이후 분석·문안 검토 → 쟁점과 유지할 강점 | 사실/요건 문제는 분석팀, 표현/누락 문제는 작성팀에 반환 |
| 조정 | 범위·공통 입력·revision 정렬, 쟁점 해결, 최종 판단과 사용자 선택 구분 | 해결되지 않는 중요 쟁점만 사용자에게 전달 |

- 위임에는 대상, 역할, 원문/owner 링크, 허용 동작, 산출물, 받을 담당자를 적는다. 요약 결론만 주지 말고 판단에 필요한 원자료도 제공한다.
- 분석과 검토는 공통 JD·evidence로 1차 판단을 먼저 남긴 뒤 서로의 종합 결론을 교환한다. 검토 담당은 가능하면 새 context로 시작해 다른 팀 결론이 아니라 원자료·평가 기준을 받는다. 필요한 원문·확인 질문은 처음부터 공유할 수 있다. 이미 결론에 노출된 검토를 blind review라고 부르지 않는다.
- 작성 담당은 분석이 진행되는 동안 기존 claim과 문서 계약을 확인할 수 있다. 분석 brief가 준비되면 그 회사부터 작성 방향을 잡고 검토로 넘긴다.
- 같은 파일의 작성자는 한 명이다. 공유 브라우저도 조정자 한 명이 제어하거나 page별 소유자를 정한다. 읽기 전용 팀이 임의로 다른 팀의 파일을 고치지 않는다.

## 3. 기존 전문 workflow를 연결한다

해당 단계를 실제 실행할 때만 아래 skill/계약을 읽는다. 규칙 본문을 팀별 프롬프트에 새로 복제하지 않는다.

| 단계 | 실행 owner | 팀이 추가하는 것 |
| --- | --- | --- |
| 현재 지원 대상·마감 확인 | [report-application-status](../report-application-status/SKILL.md) | 마감 임박은 작업 순서 신호이지 지원 여부·직무 적합도 판정이 아님 |
| 회사·JD 분석 | [analyze-jd-fit](../analyze-jd-fit/SKILL.md) | 공식 회사·제품 자료를 더해 왜 이 역할이 필요한지 해석. 공고 밖 채용 의도·성공 목표는 Inference/Unknown으로 표시 |
| 실제 문안 작성 요청 | [tailor-resume](../tailor-resume/SKILL.md) | 분석 brief의 요구와 claim을 전달하고 관련성 순서·독자 질문을 점검. 재분석만이면 작성 brief에서 종료 |
| 기존/작성된 지원 문안 검토 | [review-application-copy](../review-application-copy/SKILL.md) | 요청 회사·문서로 범위를 명시. 분석만이면 이 문안 전수 검토 workflow를 호출하지 않음 |
| 문안·제출 보호 | [Application Copy Standard](../../../wiki/rules/application-copy-standard.md), [lifecycle](../../../wiki/products/resume/application-lifecycle.md) | 변경 권한·기여 강도·검증·동결 규칙은 원래 owner가 소유 |

회사 사실은 원문 URL·확인일·직접 확인한 범위를, 개인 사실은 canonical profile/evidence의 claim ID·공개 범위·기여 강도를 붙인다. 기존 지원 문안은 검토 대상이지 개인 사실의 증거가 아니다. 구버전 skill 분류와 최신 claim이 충돌하면 owner·날짜·범위를 대조하고 drift를 밝힌다.

## 4. 팀 간에는 같은 작업 단위를 주고받는다

### Writer의 엔지니어링 전문성

작성 담당은 [개인 판단 기준](../../../wiki/profile/decision-principles.md)과 [문안 기준 §1-6](../../../wiki/rules/application-copy-standard.md)의 `엔지니어링 판단의 구체성`을 읽는다. 분석팀에 추상 역할만 받지 않고 보호 조건·실패 상황·구현 기전·검증 중 문장을 구별해 주는 실제 근거를 요청한다. 검토팀에는 표현을 바꾼 이유와 연결 claim을 넘긴다. 전문성을 위한 별도 인물 설정이나 기술 키워드 할당량은 두지 않는다.

기본 인계 단위는 파일 묶음이 아니라 **회사/공고 + brief revision + 판단할 쟁점**이다. 채팅·agent 메시지로도 충분하며 저장은 요청 범위에서만 한다.

분석 → 작성·검토:

- 회사/공고 식별자, 원문 URL·확인일, 이전 분석에서 달라진 점.
- 역할이 만들어야 할 결과, 필수·우대·불명확 조건. 회사 선택 조건(계약 형태·근무 방식 등)은 실력 적합도와 분리.
- `요구 → claim ID/근거 → strong/partial/gap/check → 앞세울 이유 또는 확인할 것`.
- 작성할 수 있는 범위와 피해야 할 과장, 판단을 바꿀 질문.

작성 → 검토:

- 같은 brief revision, 독자에게 답할 핵심 질문과 성과 선택·순서의 이유.
- 분석만이면 작성 방향, 문안 요청이면 초안 위치와 claim 연결.
- 분석팀에 반환한 근거 요청 및 아직 해결되지 않은 항목.

검토 → 담당자:

- `필수 수정 / 개선 제안 / 유지할 강점 / 미확인`으로 분리한다.
- 각 쟁점에 대상(요구 ID 또는 file:line), 근거, 영향, 제안, 담당자를 붙인다.
- 불충족 근거와 단순 미확인을 구분한다. 인접 경험으로 충분한 조건을 더 엄격하게 바꾸지 않고, 우대요건을 필수로 승격하지 않는다.

담당자는 `수용·수정 / 근거를 들어 유지 / 추가 확인 필요`로 답한다. 수정본의 revision과 바뀐 요구·claim을 보내고 검토자는 그 변경이 해소한 항목을 확인한다. 사실·요건이 바뀌면 해당 인계를 다시 열고 작성·검토의 영향 부분만 재검토한다.

## 5. 조정하고 멈춘다

- 조정자는 논쟁을 원문 해석, 증거 범위, 사용자 선호, 편집 취향으로 나눈다. 원문·근거 문제는 재확인, 근무·계약·지원 선택은 사용자에게, 편집 취향은 작성 owner에게 돌린다. 다수결·평균 점수·합격 확률로 해결하지 않는다.
- 필수 수정이 닫히고 요청한 산출물이 갖춰지면 종료한다. 개선 제안만 남으면 별도로 알리고 넘긴다. 같은 필수 검토 항목이 수정 두 번 후에도 남으면 [작업 규칙](../../../AGENTS.md)의 escalation 방식으로 사용자에게 올린다.
- **작성자의 완료 보고는 종료가 아니다.** 조정자가 실제 산출물을 읽고 합의 목록의 각 항목이 본문에 들어갔는지 대조한 뒤 수용 또는 구체적 수정 요청으로 닫는다. 자동 알림·완료 감시를 실제로 구성하지 않았으면 작동한다고 말하지 않는다.
- `아직 확인하지 못함`을 숨기고 완료 처리하지 않는다. 사용자 결정이 필요한 회사만 보류하고 다른 독립 작업은 진행할 수 있다.
- 최종에는 팀별 원문을 합쳐 붙이지 말고 회사별 판단·근거·작성 방향·검토로 달라진 점·남은 선택을 통합한다. 변경한 파일과 검증 결과는 실제 변경이 있을 때만 보고한다.
- 실제 실행한 역할·주고받은 쟁점만 보고한다. 가상 회의, 실행하지 않은 상호 검토, 자동 알림, 지원 완료를 만들지 않는다.
