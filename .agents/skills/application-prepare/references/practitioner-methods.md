# Practitioner Methods

확인일: 2026-09-06. 실무자가 공개한 절차와 우리 workflow로의 적용을 구분한다. 아래 자료는 원문 전체의 복제가 아닌 선택적 요약이다. 새 방식으로 변경할 때는 해당 출처를 다시 확인한다. 각 회사의 현재 채용 사실은 별도로 조사한다.

## 분석 — 채용 목표를 먼저 맞추는 recruiter

Source: [Sean O’Connor, Navigating a structured hiring and kickoff process](https://www.greenhouse.com/uk/guidance/navigating-a-structured-hiring-and-kickoff-process).

- 실무 주체: 글의 저자 소개상 Greenhouse Talent Acquisition Manager – Sales & Marketing. 원문은 2022-04-18과 2026-02-24를 함께 표시하므로 후자를 새 방법론의 최초 발표일로 단정하지 않는다.
- 관찰된 방식: 사업상 채용 필요·역할 목표·초기 성공 결과·협업 관계를 사전 정리하고 recruiter와 hiring manager가 역량 및 평가 담당을 맞춘다. 진행 중 어긋나면 kickoff 기록으로 돌아간다.
- 우리의 적용: 분석팀이 JD의 기대 결과와 조건을 먼저 구조화하고 모든 팀이 같은 brief를 소비한다. 공개 원문에 없는 내부 채용 목적은 가설로 남긴다.
- 제외: 이 회사의 회의 길이·주기 강제, 고용주 내부 정보가 있다는 가정, 경험 중심 평가를 이유로 JD의 명시 연차를 무시하는 것.

## 작성 — 채용 독자의 읽기 순서에 맞추는 hiring manager

Source: [Gergely Orosz, How to write an effective developer resume](https://stackoverflow.blog/2020/11/25/how-to-write-an-effective-developer-resume-advice-from-a-hiring-manager/) (2020-11-25).

- 실무 주체: 여러 회사의 hiring manager로 이력서를 검토했고 채용 담당자·매니저를 인터뷰한 저자의 경험 기반 조언.
- 관찰된 방식: 이력서 목적을 다음 채용 대화로의 연결로 두고, 해당 역할과 관련된 경험을 먼저 선택한다. 책임 목록보다 행동·결과를 구체화하고 빠른 훑어보기와 정독의 두 관점으로 읽는다.
- 우리의 적용: 작성팀은 독자 질문과 증거 선택을 설명하고 순서·상세도를 조절한다. 실제 초안은 기존 문안 계약으로 작성하며 수치는 검증된 것만 사용한다.
- 제외: 당시 ATS 관찰을 현재 모든 회사에 일반화, 고정 페이지 수, 측정하지 않은 수치 생성, 승인된 브랜드·표현 규칙의 임의 변경.

## 검토 — 독립 관찰 후 구체 근거를 대조하는 interviewer

Source: [GitLab, Conducting a GitLab Interview](https://handbook.gitlab.com/handbook/hiring/conducting-a-gitlab-interview/), `Before the Interview`, `Candidate Evaluation and Scorecards`.

- 실무 주체: GitLab 면접관·Recruiter·Hiring Manager의 공개 운영 지침. 특정 개인의 단독 방법론으로 소개하지 않는다.
- 관찰된 방식: JD와 평가 역량을 맞춘 뒤 다른 면접관의 전체 평가를 가려 편향을 줄인다. 직무와 관련된 구체 사례로 강점·약점을 기록한다. 얻지 못한 정보는 별도로 남긴다.
- 우리의 적용: 분석팀과 검토팀은 서로의 종합 결론을 보기 전 1차 판단을 남긴 후 근거를 교환한다. 지원 문서를 읽는 행위는 실제 면접 평가와 다르므로 개인의 능력·합격 여부까지 판정하지 않는다.
- 제외: GitLab의 조직 가치·등급·채용 기준 복제, 여러 에이전트를 독립적인 합격 투표로 세기, 같은 대화 이력을 읽고도 blind review라고 주장하기.

## 수정 협업 — 구체적인 대안을 주는 documentation reviewer

Source: [Google, Markdown style guide — Better is better than best](https://google.github.io/styleguide/docguide/style.html#better-is-better-than-best).

- 실무 주체: Google 내부 기술문서 작성자·리뷰어에게 공개한 검토 지침. 이력서 전문 방법론은 아니다.
- 관찰된 방식: 모호한 지적 대신 대안을 제안하고 큰 범위의 요구는 후속 작업으로 분리한다. 사소한 취향 논쟁으로 진전을 막지 않는다.
- 우리의 적용: 검토 의견마다 영향·담당·수정안을 붙이고 필수 수정과 개선 제안을 분리한다. 해소된 쟁점은 닫고 유지할 강점도 전달한다.
- 제외: 빠른 승인을 사실 검증·공개 범위·사용자 승인 생략의 근거로 삼는 것.

## 우리 설계가 소유하는 부분

분석·작성·검토 3역할, 조정자, claim ID, brief revision, 단일 파일 작성자, 단계별 권한은 위 출처의 원문 절차가 아니다. 이 workspace의 evidence·문안·lifecycle 정책과 사용자 팀 운영 요청을 결합한 구현이다. 외부 실무자가 이 시스템의 효과를 보증한 것처럼 표현하지 않는다.
