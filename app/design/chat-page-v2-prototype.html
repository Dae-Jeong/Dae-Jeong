중앙 정렬 인사+suggestion(GPT식) vs 상단 좌측 정렬 문서형

빈 대화 화면은 상단 좌측 정렬 문서형으로 결정. GPT/Claude처럼 화면 중앙에 큰 인사말을 띄우지 않고, nav 바로 아래에서 좌측 정렬로 정체성 한 줄 + 짧은 규칙 설명 + suggestion을 세로 넘버드 리스트(01–03)로 쌓는다. suggestion은 기존 확정 질문 3개를 그대로 재사용.

중앙 정렬을 택하지 않은 이유: GPT의 중앙 정렬 인사말은 “무엇이든 물어보세요”라는 열린 범용 어시스턴트 약속을 시각적으로 암시한다. 이 사이트의 에이전트는 반대로 검증된 claim registry의 public 표현만 답하는 좁고 정직한 도구다. 화면 한가운데의 커다란 환영 인사는 이 제품이 실제로 할 수 있는 것보다 더 많은 걸 약속하는 것처럼 읽혀 정체성과 충돌한다.

문서형이 이 사이트에 맞는 이유: mono 시스템은 좌측 인덱스·하드 그리드·doc형 컨테이너가 규율이다(root·portfolio·resume 프로토타입 모두 상단 좌측 정렬). 빈 상태만 중앙 정렬로 바꾸면 사이트 안에서 이 화면 하나가 이질적으로 뜬다. 넘버드 suggestion 리스트는 순번(01–03)이 곧 읽는 순서가 되어 mono 문법과 정합하고, GPT의 “빈 상태는 시작점을 제시한다”는 핵심 목적도 그대로 달성한다.

택: 상단 좌측 정렬 문서형 / 반: 중앙 정렬 인사+suggestion 카드(GPT식)
결정 · 우측 bubble 유지 D2 · 사용자 메시지 표현

우측 bubble(기존) 유지 vs 플랫 행으로 통일

사용자(Visitor) 메시지는 우측 정렬 bubble을 유지하고, assistant(Profile Agent)는 기존대로 좌측 보더 플랫 본문으로 둔다. GPT/Claude의 “assistant는 플랫” 규칙은 이미 따르고 있으므로, 바꾸는 건 사용자 메시지를 플랫으로 통일하느냐뿐 — 통일하지 않기로 결정.

플랫 통일을 택하지 않은 이유: assistant 답변은 본문 여러 문단 + evidence chip + related link로 정보 밀도가 높다. 사용자 질문까지 같은 좌측 플랫 행으로 통일하면 “누가 물었고 누가 답했는지”의 경계가 흐려져, 한 화면에 문답이 여러 번 쌓일수록 스캔이 어려워진다. 우측 bubble은 화자 전환을 레이아웃만으로 즉시 구분해 주는 가장 값싼 신호다.

mono 규율과 충돌하지 않는 이유: bubble은 --surface 배경 + radius 0 사각형으로, GPT식 둥근 말풍선이 아니다. 색·라운드를 쓰지 않고 정렬(우측)과 배경 톤만으로 구분하므로 mono의 하드 그리드 문법 안에 그대로 들어온다. 근거 rail이 assistant 답변에 붙는 구조라, 사용자 발화를 시각적으로 가볍게(짧은 우측 블록) 두는 편이 밀도 대비가 살아 오히려 읽기 리듬이 좋아진다.

택: 우측 bubble 유지 / 반: 사용자·assistant 모두 플랫 행 통일
