결정 · Sticky rail DECISION · 상세의 rail

resume식 sticky rail(목차 + 케이스 이동) vs 본문 단독 + 하단 내비만

상세 페이지는 우측 sticky rail로 결정. rail에는 목록으로 버튼 · 이 케이스의 목차(문제·검토·결정·시스템·결과) · 다른 케이스로 이동 리스트를 담고, 스크롤 위치에 따라 목차 활성 항목을 갱신합니다. 하단 이전/다음 내비는 rail과 중복이 아니라 역할이 다릅니다 — 하단은 순차 이동, rail은 임의 점프.

본문 단독 + 하단 내비만으로 하지 않은 이유: 상세는 문제 → 검토 → 결정 → 시스템 → 결과 5단으로 세로가 길어, 본문만 두면 독자가 지금 어느 단락인지와 얼마나 남았는지를 잃습니다. 특히 면접관이 “검토”나 “결과”만 바로 확인하려 할 때, 하단까지 스크롤해야 다른 케이스로 넘어가는 구조는 왕복 비용이 큽니다.

resume 패턴을 재사용하는 이유: resume-page가 이미 우측 rail(PDF·언어·목차)을 doc형 레이아웃의 확정 패턴으로 씁니다. 같은 doc 폭(1180/28)·같은 sticky rail을 상세에도 쓰면 문서 계열 페이지의 일관성이 유지되고, 새 레이아웃 문법을 만들지 않습니다.

택: sticky rail(목차+케이스 이동) / 반: 본문 단독 + 하단 내비만
12차 · 4단 → 5단 DECISION · 케이스 서술 구조

「검토」를 신설해 문제 · 검토 · 결정 · 시스템 · 결과 5단으로 — 기각한 대안을 본문에 세운다

기존 문제 · 결정 · 시스템 · 운영 근거 4단에 검토를 추가했습니다. 검토에는 기각 2건 + 채택 1건을 같은 층위에 나란히 놓고, 각각 왜 버렸는지를 한 줄로 답니다.

기각안을 굳이 보여주는 이유: 기존 4단은 문제 → 결정이 곧바로 붙어 있어, 결정이 유일한 선택지였던 것처럼 읽혔습니다. 실제로는 부분 수정·전면 교체를 함께 검토하고 버린 판단이 있었는데 그 과정이 지면에 없었습니다. 근거는 양쪽이 같은 것을 요구합니다 — 국내(서치라이트) “면접관은 Action보다 Analyze를 중요하게 봅니다”, 해외 “the messy middle — 검토했다가 기각한 대안”. 즉 읽는 사람이 확인하려는 건 무엇을 했는가보다 왜 그것이어야 했는가입니다.

「검토」를 결정 앞에 둔 이유: 시간 순서이자 논증 순서이기 때문입니다. 문제에서 원인이 구조임을 확인하고 → 어디까지 손대야 그 구조가 사라지는지 비교한 뒤 → 결정이 나옵니다. 결정 뒤에 두면 이미 내려진 결론을 사후 정당화하는 것처럼 읽힙니다.

기각/채택을 색으로 나누지 않은 이유: Mono 계약은 색·간격 문법을 이번 라운드에서 바꾸지 않는다는 제약이 있고, 기각은 --danger로 칠할 성질도 아닙니다 — 틀린 안이 아니라 이 조건에서 선택하지 않은 안입니다. 그래서 좌측 상태 마커(— / ▸)와 제목 굵기·본문 색 단계만으로 구분했습니다.

택: 검토를 결정 앞 독립 섹션(기각 2 + 채택 1) / 반: 결정 안에 각주로 편입(Analyze가 다시 묻힘) · 색으로 기각 표시(색 문법 변경)
12차 · 번호·rail 자동 계산 DECISION · 선택 섹션이 빠져도 안 깨지는 구조

섹션 번호와 sticky rail을 하드코딩하지 않고 실제 섹션에서 파생시킨다

검토와 한계·다음 수는 근거가 없는 케이스에서 통째로 빠집니다. 그래서 .c-sechead__no를 빈 채로 두고, rail <ol>도 본문 .case-sec에서 생성합니다. 섹션 하나를 지우면 번호와 rail이 자동으로 다시 이어집니다.

하드코딩을 금지한 이유: 번호가 마크업에 박혀 있으면 선택 섹션을 뺄 때 세 곳(본문 번호 · rail 번호 · rail 항목)을 동시에 고쳐야 하고, 하나라도 놓치면 01 · 03 · 04처럼 번호가 튀거나 rail에 죽은 링크가 남습니다. 케이스가 5건으로 늘어나면 이 실수는 반드시 납니다 — 구조로 막는 편이 싸습니다.

no-JS 폴백을 남긴 이유: rail을 스크립트로 생성하면 JS가 죽었을 때 목차가 빈 칸이 됩니다. 그래서 마크업에 현재 5개 항목을 그대로 적어 두고, 스크립트가 켜지면 즉시 교체합니다 — 최악의 경우에도 목차는 보입니다.

택: 번호·rail을 .case-sec에서 파생(+ no-JS 폴백) / 반: 번호 하드코딩(섹션 누락 시 3곳 동시 수정) · rail 전체를 JS 생성(JS 실패 시 빈 목차)
12차 · 운영 근거 → 결과 · 토큰 동기화 DECISION · 마지막 단락의 이름과 이 파일의 스케일

「운영 근거」를 「결과」로 바꾸고, 이 파일의 타입 스케일을 9·12차 계약으로 올린다

개칭했습니다. 근거 chip(popover) 문법과 섹션 id="ops"는 유지합니다. 함께: 이 파일도 resume-page처럼 계약에서 이탈해 있어(base 14 · xs 11 · sm 12, 10px 하드코딩 6곳) 토큰을 xs 12 · sm 13 · base 16 · lg 18 · xl 22로 올린 뒤 섹션 제목에 --text-2xl을 적용했습니다.

「결과」가 더 맞는 이유: PAAR의 R은 Result이고, 이 단락이 답해야 하는 질문은 “근거가 있나”가 아니라 “그래서 어떻게 됐나”입니다. 「운영 근거」는 증빙의 성격을 이름에 박아 두어, 정작 결과가 무엇인지는 독자가 chip을 눌러야 알 수 있었습니다. 이름은 결과로 바꾸고 증빙은 그 안의 chip이 계속 맡습니다.

id를 바꾸지 않은 이유: #ops는 popover 내부 링크가 가리키고 있어, 이름과 함께 바꾸면 죽은 링크가 생깁니다. 표시 이름과 앵커 id는 수명이 다르므로 같이 움직일 이유가 없습니다.

「한계·다음 수」를 결과 안에 둔 이유: 별도 섹션으로 세우면 rail에 06 한계가 생겨 결과와 대등한 무게를 갖습니다. 이건 결과의 단서이지 독립 단락이 아니므로, 결과 말미에 구분선으로 붙여 “여기까지가 결과, 이건 그 한계”로 읽히게 했습니다.

택: 결과로 개칭(id 유지) · 한계는 결과 내부 블록 · 토큰 9·12차 동기화 / 반: 운영 근거 유지(R이 증빙으로 읽힘) · 한계를 6번째 섹션(무게 과대) · 토큰 이탈 방치

문제

Problem

AI 콘텐츠 생성 제품 Thready의 backend를 인계받았을 때, 생성 품질이 프롬프트·모델 호출에 흩어져 있어 무엇이 좋은 출력인지 판정하고 회귀를 잡을 기준이 없었다. 프롬프트는 문자열로 조립되어 타입 안전성과 재사용이 약했고, 실패·품질 저하를 관측할 로깅 축도 부족했다.

원인이 특정 코드가 아니라 구조에 있었으므로, 어디까지 손대야 이 구조가 사라지는지부터 정해야 했다.

검토

Alternatives

재구축은 되돌리기 어려운 선택이라 세 가지 경로를 먼저 비교했다. 판단 기준은 두 가지였다 — 문제의 원인인 의존성 구조가 실제로 사라지는가, 그리고 실패했을 때 영향 범위(blast radius)가 감당 가능한가.

기각 부분 수정 — 문제 구간만 고쳐 쓴다 가장 싸 보였지만 의존성 구조가 그대로 남는다. 품질 판정 기준이 없다는 원인은 특정 함수가 아니라 구조에서 나오므로, 고친 자리 옆에서 같은 문제가 다시 자란다.
기각 전면 교체 — FE 포함 제품 전체를 다시 만든다 구조는 확실히 사라지지만 blast radius가 과대하다. 원인이 backend에 있는데 FE까지 끌어들이면 실패 지점이 늘고, 되돌릴 수 없는 구간이 길어진다.
채택 backend만 분리 교체 — 경계를 긋고 그 안쪽만 재구축 원인이 있는 범위와 교체 범위를 일치시킨다. 결정적으로 서비스가 작은 지금이 가장 싸다 — 트래픽·연동·데이터가 더 늘기 전에 치르는 비용이 나중보다 작다. FE 계약을 유지한 채 cutover하면 되돌릴 지점도 남는다.

결정

Decision

품질을 “감”이 아니라 시스템으로 다루기 위해 세 가지를 결정했다.

Typed Prompt프롬프트를 문자열이 아닌 typed prompt builder로 구성 — 입력 계약을 타입으로 고정하고 재사용 가능하게 만든다.
Judge LoopLLM judge 기반 평가 루프를 도입 — 출력 품질을 판정 가능한 축으로 만들어 회귀를 감지한다.
Observability관측 로깅을 표준으로 심어 — 생성 흐름과 실패를 사후에 추적할 수 있게 한다.

시스템

System

결정을 실제 backend 구조로 옮긴 결과, 생성 품질이 재구축된 FastAPI backend 위의 시스템으로 자리 잡았다.

Typed Prompt Builder

프롬프트 조립을 타입으로 계약화 — 입력 누락·형 오류를 호출 전에 차단하고 재사용을 표준화.

LLM Judge · 평가 루프

생성 출력을 judge로 채점하는 루프 — 품질을 판정 가능한 값으로 만들어 회귀 감지에 사용.

관측 로깅

생성 흐름·실패 지점을 로깅 — 운영 중 문제를 사후 추적하고 원인을 좁힘.

Rebuild + Cutover

부분 패치가 아닌 전면 재구축 후 cutover — 이후 개발·운영을 전담하는 단일 오너십.

한계 · 다음 수

judge는 회귀를 감지하지만 아직 릴리스를 차단하지는 않는다 — 판정이 사람의 확인을 거쳐야 하는 단계다. 다시 한다면 평가 루프를 재구축과 같은 시점에 세우겠다. 지금은 cutover 이후에 붙였기 때문에, 재구축 전후를 같은 축으로 비교할 기준선이 남지 않았다.
